# 官网：单页站点（2026-09-21）

> **本文是 `site/` 的权威设计。** 它**取代** `docs/design/site.md` 与
> `docs/design/site-rebuild/`（28 页重构那一批）——后两者只作为历史存档保留。

一条命令验收：

```bash
python3 scripts/check-site.py            # 10 项，exit 0 才算过
python3 scripts/check-site.py --browser  # 额外跑真 Chrome（资源零 404 + 版本回填）
```

---

## 1. 为什么推倒

用户 2026-09-21 的原话：

> site 刚刚被重构了，但是属于灾难，你把所有 site 简化吧：单个网页，只说明：
> 是什么，怎么安装，有什么核心特点，未来的计划。这几件事情。

前一天（2026-09-20）的 28 页重构在**视觉**上是有主张的（D1 的「方格纸 · 朱批」
是站得住的），但它把**维护面**做大到了与产品不匹配的程度：

| 重构后的东西 | 规模 | 问题 |
|---|---|---|
| 手写页面 | 28 页 | 一个 3 人以下的仓库没有能力同步维护 28 页的事实 |
| 生成器 / 检查器 | 11 个脚本，约 6800 行 | 比被检查的站点本身大两个数量级 |
| 生成数据 | 8 份 JSON，约 400 KB | 走查 / 事件流 / 时间线 / 诊断码表——**没有任何读者** |
| 检查项 | `site-verify.py` 18 项 + `check-site.py` 10 条 | 大部分检查的对象是"28 页"这个结构本身 |

代价是实测出来的，不是感觉：重构落地后**第一次 push，站点流水线就红了**，
而红的原因是 `pages.yml` 还在调用重构中被删掉的脚本——**检查器比被检查物
活得更久**，这正是"没有对象可查的检查会腐烂成噪声"。

## 2. 现在是什么

```text
site/
  index.html          ← 唯一的页面（四个大节）
  assets/site.css     ← 唯一的样式表（令牌 + 组件，自带亮/暗两套）
  assets/site.js      ← 唯一的脚本（主题切换 / 版本回填 / 复制）
  assets/fonts.css    ← 自托管 Latin 子集（+ fonts/*.woff2，符号覆盖）
  data/site.json      ← 生成物：已发布版本（**唯一**版本号来源）
  favicon.svg  robots.txt  sitemap.xml  llms.txt  .nojekyll
```

页面只有四节，顺序就是用户点名的顺序：

1. **是什么**——共享画布 + 内核判卷，配一个真实的目标状态块（假设 / `⊢` 目标）；
2. **怎么安装**——三条路（VS Code 扩展 / CLI tarball / 仓库内 `scripts/soko`），
   每条给一条可复制、可直接执行的命令；
3. **核心特点**——8 条编号清单，每条是"断言 + 它的判据/命令"；
4. **未来的计划**——6 条**还没做**的事，用朱色标注（这是朱批的第三种合法用法：
   诚实的限制）。

## 3. 保留了什么，为什么

**设计语言整体保留**，一个字都没改：方格纸背景、发丝线（推理横线）、零圆角结构
容器、绿=内核通过过的东西 / 朱=诊断与限制的语义纪律、17px 中文锚点、40rem 行长、
自托管字体子集。理由：这些是**从题目推出来的**选择（产物是判定 ⇒ 颜色由判定驱动；
材料是方格纸上的推导 ⇒ 视觉语言取工程方格纸），不是模板默认值，而且它们在
28 页重构里已经被逐条实算过对比度。单页化没有推翻它们的理由。

**被删掉的是规模，不是主张。**

## 4. 防漂移的机制（留下的部分）

只有三条，都是"没有它就会写错"的：

| 机制 | 在哪 | 为什么必须有 |
|---|---|---|
| 版本号只有一个来源 | `scripts/gen-site-data.py` → `site/data/site.json` → `site.js` 回填 | 站点写的是**已发布版本**的事实。手写版本号会写出"没有 tag、没有产物、没有下载 URL"的版本（2026-09-20 实测踩过） |
| 已发布 = 最新 `vX.Y.Z` tag | 同上（**不是** `Cargo.toml`） | 本仓库常有并行开发，`Cargo.toml` 会先于 tag bump |
| 一条命令验收 | `scripts/check-site.py` | 见下 |

`check-site.py` 的 10 项：`pages`（恰好一页、无内部目录）、`sitemap`（与页面集合
**双向**相等）、`links`（站内引用与锚点可解析）、`css-urls`（字体文件存在）、
`version`（零写死版本号 + 回填钩子存在）、`meta`（head 元数据齐全 + 只允许一段
内联 script）、`markup`（标签配对 + 无内联 `style=`）、`assets`（零位图 + 体积预算
120 KB）、`data`（与最新 tag 一致）、`render`（可选，真 Chrome：零 404 + 版本已回填）。

**这些检查全部落在"这一个页面"上，没有一条是为了维持结构而存在的。**

## 5. 发布之后要做什么

站点锚在 tag 上，所以**发版本身就会让它过期**。两步都已在流水线里：

1. `pages.yml` 挂了 `release: types: [published]` ⇒ 发布后自动重新部署，
   部署时 `gen-site-data.py` 重算 `site/data/site.json`；
2. 工作树里那份 `site/data/site.json` 仍指向旧版本，直到有人跑一次
   `python3 scripts/gen-site-data.py`（收尾义务里已列为发布后一步）。
   **`check-site.py` 的 `data` 项会因此判红**——这是有意的：本地绿必须意味着
   "仓库里写的就是线上写的"。

## 6. 已知边界

- **单页放不下细节**：tactic 白名单、诊断码表、语言子集的完整边界都只在仓库
  文档里（`docs/design/`）。页面只给"是什么 + 去哪看"，不试图成为手册。
- **中英双语已取消**：`site/en/` 随重构删除。理由：用户点名的是"单个网页"，
  而双语单页的维护成本（两份事实要同步）换不来一个 3 人仓库的读者增量。
  要恢复就得接受"两个页面"这个前提，那是另一个决定。
- **`--browser` 不在 CI 里跑**：CI runner 装 Chrome 的收益不如把这一步留作发布前
  的本地门禁（命令见文件头）。
