# 怎么把这份文件适配成 dsh 的 goal

## 先看 goal 的硬约束（读 `~/.dsh/profiles/node_modules/@deepseek-ai/dsh-goal` 等四包文档得出）

| 约束 | 内容 | 对本文件的后果 |
|---|---|---|
| **每会话一个 goal** | 未完成的 goal 必须先 `edit`/`pause`/`block`/`clear` 才能被替换；已完成的可直接替换 | **不能一个 goal 装全部 23 个环节** |
| **`objective` 是短字符串** | 不是文件、不是路径列表 | 427 行塞不进去 |
| **Round 上限默认 256** | `defaultMaxGoalRounds`，约束**自动续行**；create 时可自带上限覆盖 | 上一轮 goal **32 轮只做完 6/7 项** ⇒ 要按轮次预算切分 |
| **goal 不存附件状态** | `/goal <objective>` 的附件只变成一条会话消息（附固定文本 `Reference attachments for the goal objective.`），后续 Round 从**会话历史**读 | ⚠ **靠附件不稳** —— 我们刚把 compaction 阈值 0.8→0.45，附件会被更频繁压掉 |
| **续行是进程本地** | 会话开始边界后 `active` goal 的续行**被停用**，必须显式 `resume` | 每次重开/恢复会话后要记得 resume |
| **block 是唯一带策略码的 phase** | `blockedReason` 有稳定 lower-kebab-case code + 说明；`block` 后**不会自动恢复** | 卡住时要人来拍板或手动 resume（今天实测过一次：`model-reported` 后会话静默 10 小时） |

## 适配方案：**三件事**（缺一不可）

### ① 文件进仓库（**不要只靠附件**）

把这份总账落到仓库里，成为**持久、可 diff、可被 git 追踪**的真文件，建议：

```
docs/PLAN-0.74-0.79.md          ← 本文件（总账 + 环节拆解 + goal 清单）
```

**理由**：goal 状态存在会话日志里，附件靠会话历史 ⇒ **compaction 会把附件压掉**。
写进仓库则任何新会话、任何 Round 都能按路径读到，且能跟着代码一起演进。

### ② objective 只写「本轮做什么 + 怎么算做完 + 要不要发版」

objective 的**形状**照抄上一轮那条成功 goal 的写法（它跑完 32 轮交付了 6/7 项）：

> 「按用户 ⟨日期⟩ 专项要求推进「⟨主题⟩」：⟨条目⟩· ⟨条目⟩· ⟨条目⟩；每条先判红、一处一 commit、
> 带反向验证，最终给「看得见的变化」清单并登记 REQUIREMENTS §9。」

即：**枚举条目 + 统一纪律 + 收敛物**。**不写**细节（细节在仓库文件里，写路径）。

### ③ 一个发版点 = 一个 goal（**因为每会话只有一个 goal**）

23 个环节分成 **7 个 goal**，每个 goal 收尾时 `complete`，再 `create` 下一个。

1. **一个会话只放一个 goal**。今天实测过两条会话同仓互相干扰，且发消息的脚本会送错会话
   （它写死点标题选会话）⇒ **别在多条会话里各建一个 goal**，选一条专职推进。
2. **goal 的轮次预算要留余量**。上一轮 goal 32 轮做完 6/7 项，且它在最后一项上**撞了 18 轮**
   才降级 —— 所以每版的轮次上限按"环节数 × 5 轮 × 2"给，别算得太紧。
3. **`block` 之后不会自己醒**。今天实测：goal 被 `model-reported` 标 blocked 后，会话静默了
   **10 小时**，还烧掉了 4.6 亿 token 的上下文。⇒ 卡住时要么立刻有人拍板，要么显式 `resume`。
   **`blockedReason.code` 要区分**：`round-limit`（预算闸，resume 有用）vs `model-reported`（它在等人）。
4. **会话开始边界后要 `resume`**（续行是进程本地的，重开/恢复会话后自动续行被停用）。
5. **完成一个 goal 就 `complete` 再 `create` 下一个** —— 别用 `edit` 把下一个版本续上去，
   否则"这一版到底做完没有"会失去界标。
6. **goal 里那条统一纪律（先判红 / 一处一 commit / 反向验证）别省** ——
   它不是装饰：今天查出来那个"F12 自跳"的 bug 能在台账里写着 `fixed`，
   正因为判据只断言"非 null"、且**没有反向验证**。

# 防翻车设计（2026-09-27 实测复盘）

> 你的原话：「这个项目管理，**又容易翻车**」。这个担心**有依据** —— 下面这张表全是
> 2026-09-27 一天内**真实发生**的翻车，不是假想。

## 今天实际翻了 7 次车 —— 而且全是同一个形状

| # | 翻车 | 根因（共同点：**账面绿、实际坏**） | 守卫落在哪 |
|---|---|---|---|
| 1 | CI「**连续 6 次绿**」是假的 | 那几次是纯 docs 推送 ⇒ `changes` 过滤器判定 rust/courses 没变 ⇒ **test / gates-course / ledger / e2e 全部 skipped**，只有快 job 跑 | **「真绿」定义**：skipped 不算绿；要有一个**逐 job 检查**的判定脚本 |
| 2 | 台账写着 **G-37 `fixed`**，实际 8 条 F12 原地跳 | 判据只断言 `summary !== 'null'`（**有答案**），**没断言落在哪一行**（答案对不对） | **E00** 判据强度普查 + 变异测试 |
| 3 | goal 被标 blocked 后**静默 10 小时** | `model-reported` 的 block **不告警、不唤醒**，而它其实是在等人拍板 | watcher 按 `blockedReason.code` **分类**：`round-limit` 才自动 resume，`model-reported` 必须**告警** |
| 4 | 两条会话**共用同一个工作树**，提交分不清谁是谁 | 无隔离、无锁 | **X2 改成 worktree 优先** |

| 6 | `docs/perf/ledger.jsonl` **停在 0.68.0**，落后 4 个版本 | 没有任何守卫要求它更新；`perf-gate` 还是「只报不拦」 | **E17** |
| 7 | 后台任务跑了 **30 分钟黑箱**，不知道为什么慢 | 输出只在**内存环形缓冲**，不落盘、外部观测不到 | **D10 / E18**（落成可判红的守卫） |

**共同根因只有两条**：① 没有「**早点发现坏了**」的信号；② 坏了以后没有「**便宜回退**」的路径。

## 三条设计原则（照着这三条，翻车就变成可控事件）

1. **每个环节必须自带红/绿信号**，而且信号要**断言具体值** —— 不是"非 null"、不是"exit 0"、
   不是"数量 > 0"。**信号在环节内部**，不许等到整批结束才知道。
2. **每个发版点必须是一个回退点** —— 一版一发一 tag。坏了 `git revert` 回上一个 tag，
   **回退面 = 这一版**，不会牵连别的。
3. **坏消息必须能自己找上门** —— 不许依赖人主动去查。今天的 3 / 6 / 7 三条**全都是人查出来的**，
   没人查就永远不知道 —— 那才是真正的代价。

## 开工前的 5 个前置（不满足就别开）

| # | 前置 | 现状 |
|---|---|---|
| 1 | **判据强度到位**（E00 做完） | ❌ 未做 —— 不做这个，后面每个环节做完都**看不出来** |
| 2 | **「真绿」定义**（逐 job 判定，skipped 不算绿） | ❌ 未做 |
| 3 | **隔离**：一条会话一个 worktree | ❌ 未做（skill 已在清单上游，加两行即可） |
| 4 | **磁盘**：`target/` 曾 **205 GB**（`deps/*.rcgu.o` **966,858 个 / 171 GB** · `incremental/` **82 GB**） | ✅ **已清 + 守卫已就位**（2026-09-27 15:00 清到 **2.0 GB** —— **不是待办** ✓）<br>① **不动增量编译** ✗✓（用户 2026-09-27 拍板：**性能/迭代速度优先** ✓；依据 `~/.cargo/config.toml` 2026-09-26 那条**已批准**记录「不要全局关增量」✓）<br>② 磁盘走**守卫 + 回收** ✓：`python3 scripts/target-hygiene.py`（`target/` **40 GB 报警 / 100 GB 判红** —— 日常不误触发 ✓）<br>③ 回收：`rm -rf target/debug/deps target/debug/incremental`（⚠ 本机 **`cargo clean` 会被 EPERM 拦** ✗）<br>④ 实测（探针改内容强制真重编 ⇒ 绕开 Fresh 与 sccache ✓）：`incremental ON ⇒ 一次重编 Δ=+233` 个 `.rcgu.o`（522→755）· `OFF ⇒ Δ=0` |

## 每个环节的 4 条硬判据（缺一条就不算做完）

1. **先判红** —— 改之前让判据红过（不许"改完直接绿"）。
2. **断言具体值** —— 落点行号 / token 类型 / 计数，不是"存在"。
3. **反向验证** —— 撤掉修复必须判红。**不做这一步就等于没有判据。**
4. **一处一 commit** —— 提交信息里写清判据。

## 翻车后的 3 步（把损失压到最小）

1. **停**：同一处连红 3 次 ⇒ **换招或降级**（本仓已有这条纪律，今天 B2 就是靠它止损的）。
2. **退**：`git revert` 到最近的发版点。因为一版一发一 tag，**回退面很小**。
3. **记**：把"已排除什么、还剩什么"写进 `docs/gaps/ledger.jsonl`，
   别留一个模糊的"在修中"——**模糊态是下一次翻车的温床**（今天的 kernel 性能就悬在这种态里）。

## 一条要接受的现实

**不能保证不翻车。** 能保证的是两件事：翻车**早被发现**（信号在环节内，不靠人查）+
**便宜回退**（离一个 tag 的距离）。

今天 7 次里有 **5 次是「翻完很久才被人发现」**，那 5 次才是真正的代价 ——
本设计要消灭的正是这 5 次。
