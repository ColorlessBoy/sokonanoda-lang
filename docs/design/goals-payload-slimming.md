## 1. 读数（实测，先量后动 ✓）

| 项 | 值 | 怎么量的 |
|---|---|---|
| `soko/goals` 请求往返 | **5.9ms** | `PERF goals-wallclock`（真子进程 ✓） |

| 往返底噪 / 内核探针 | 0.0ms / ±0.2ms | `PERF rpc-floor` / 开关 A-B |

⇒ LSP 那 3.7ms 的**主因是载荷**：每条声明的 `ty_runs` / `goal_runs` / `value_runs` 把
**每个 token** 都做成一条 `RunInfo`（`{text, kind, start, end}`）⇒ 91KB 要序列化 + 客户端解析**每次**。
**对照 Lean**：`$/lean/plainGoal` **只回目标文本** ✓ ⇒ 这一格的差距是**协议形状**，不是编译慢 ✓。

## 2. 契约（改动面与红线）

* **加法式**：新增**可选**字段承载紧凑编码；**旧字段一律保留**（老客户端继续工作 ✓）。
* **消费者**：`editor/vscode/`（真正读 runs 的人 ✓）· `skills/`（写协议的说明 ✓）·
  `docs/protocol.md`（**契约唯一权威** ✓）⇒ **必须同一轮同步** ✓。
* **红线**：`--json` 事件流与判卷**不受影响** ✓（本设计只动 `soko/goals` 这一条自定义请求的**可选**字段 ✓）。
* **不许**删旧字段、不许改语义 ✗ —— 要下线走**弃用流程**（先文档标注、后大版本删 ✓）。

## 3. 候选编码（择一，实现前先各量一次 ✓）

| 候选 | 形状 | 体积估计 | 风险 |
|---|---|---|---|
| **A. 稀疏 runs** | 只发 **kind 变更点**：`[{start, kind, len?}, …]` ⇒ 客户端线形展开 ✓ | 91KB → **~5–10KB** | 客户端要改解析 ✓；等价性需判据 |
| **B. 按需索取** | 请求加 `runs: "none" \| "all"`（缺省 `all` ✓ 旧行为不变 ✓） | 视客户端而定 ⇒ **~24KB**（只剩 `text`） | 扩展要发两次请求或自己再要一次 ✓ |
| **C. 表化** | runs 去重成**字典 + 下标**（kind 与 text 高度重复 ✓） | ~10–20KB | 解析复杂度上升 ✓ |

**倾向**：先量 A 的真实压缩比与等价成本 ✓（`runs` 的 kind 段本来就连续 ✓ ⇒ 稀疏化天然合适 ✓）。
