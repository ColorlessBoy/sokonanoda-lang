## ① 这个设计从哪来

**引入 commit**：`f4a92994`（2026-09-18 07:43:12）`feat(front,cli): I16 P4 —— 闭包哈希缓存（依赖变则入口必 miss）`。
`git log -S 'pub fn digest' -- crates/front/src/project/mod.rs` **只回这一条**（父提交里 `digest` 出现 0 次）。

**当时的理由（commit message 原文）**：

> - `project::plan_project / compile_plan` 拆分：闭包摘要必须在编译**之前**算出来才能查缓存；
>   `ProjectPlan::digest` = 拓扑序全模块源文本 + import 边 + prelude 模式
> - 只缓存完全干净的项目（`ProjectReport::is_clean`）：条目只含入口报告/事件，带诊断的项目
>   回放不出依赖诊断，而冷/热跑必须一致

**当时的代码注释**：

> `/// 闭包摘要：**所有模块的源文本按拓扑序** + import 边 + prelude 模式。`
> `/// 依赖变了 ⇒ 摘要变 ⇒ 入口的缓存键变（设计 §4.8 的 Merkle 链）。`

⇒ **假设是**：键必须覆盖**整条闭包**才算 sound（Merkle 链：依赖变 ⇒ 入口必 miss）。
这个假设**本身没错**——错的是它被当成**唯一**要满足的性质：**"多个入口共享依赖"这一情形
在设计文档里从未被讨论**（不是被否掉，是**没被想过**）。

**设计里其实写了另一半，但没实现**：`docs/design/imports-and-projects.md:256` 的
`### 4.8 D7 —— 缓存：闭包哈希（Merkle），报告按模块存` 同时写着：

> `:271` **报告缓存键 = `iface(入口文件)`** …
> `:273-274` **按模块存**：`<cache_root>/compiled/<iface>.json` 存 `{format, report}`，
> `report` 内含该模块的 `ModuleReport`；**`build` 可以预热整个项目的每个模块**。

⇒ **设计自己就是矛盾的**：`:271` 说键按**入口**、`:273` 说存**按模块**并"预热每个模块"。
实现取了 `:271`（每入口一条），`:273` 那句"每个模块"**从未落地**。
（诚实边界：这是**设计内部的口径冲突**，不是"实现偷偷违背设计"——两种读法都讲得通。）

**假设什么时候失效：一上来就错，不是规模触发。** `f4a92994` 当时**全仓没有一个含 `import`
的 `.sokonanoda`、也没有任何 `sokonanoda.toml`**（逐文件扫 `git ls-tree -r` 验证）——
唯一的多模块项目是 `crates/cli/tests/imports.rs` 里的 **2 文件测试夹具**。
课程第二天（`347bd836`）诞生时就已经 **4.09×**。静态闭包阶梯（按源码 import 边重算）：

|---|---|---|---|
| `v0.60.0`（2026-09-19，课程诞生当天） | 35 | 144 | **4.11×** |

⇒ **重复比几乎恒定（4.05–4.14×）**，涨的只是**绝对**墙钟。所以"课程小时无感"只对了一半：
**不是小时不成问题，是小时没人量过**——键从没在**有共享依赖的语料**上验证过。

## ③ 防复发的守卫（**已实现**，能判红）

**设计原则**：既有体系全是**相对量** ⇒ 新守卫必须测**绝对次数**，而且**与规模无关**
（否则课程长大就假红——正是 E17 归一化想避免的那件事）。

**实现**：`scripts/check-recompile-factor.py`（上界 `scripts/recompile-budget.json`，**只许减不许增**）

* **夹具**（临时目录、自足）：`lib/Shared.sokonanoda` **恰好 1 个 `by` 证明** + 3 个入口
  各 `import lib.Shared`（入口自身项风格、0 个 `by`）；
* **读数**：`SOKO_STAGE_STATS=1` 的 `by_calls` = **`by` 引擎被调用次数** ⇒ 共享依赖每被
  elaborate 一次 +1（入口不贡献）⇒ 它就是"**共享依赖被编了几次**"的直接读数；
* **判据**：`by_calls ≤ max_by_calls`（今天 = **3**；**修好后应为 1 ⇒ 届时收紧到 1**）。
  实测今天：3 入口 ⇒ `by_calls=3`、Σ闭包 6 次编译 vs 去重 4 个模块；
* **反向验证**（`--selftest`，也进 gate）：单入口 ⇒ 不红 · 今天基线 ⇒ 不红 ·
  **5 入口共享 1 依赖（造重复）⇒ 必须判红** ✓ · 3 个独立依赖（无从省）⇒ 不红 ✓ ·
  `by_calls=0`（计数器失效）⇒ **exit 2，绝不静默通过** ✓；
* **接线**：`scripts/soko gate`（`--fast` 也跑，~1s）+ CI `gates-fast` 一步
  （二进制用上一步刚 `cargo build` 的 `target/debug/sokonanoda`——判据是**结构计数**，
  与 debug/release 无关）。

**它挡什么 / 不挡什么**（诚实边界）：它挡"**重复功变多**"（今天 3 是缺口值、不是健康值）；
**它不证明 3 是对的**——把 3 变成 1 是 G-68 本体，由 `docs/gaps/repro/G68-*.sh` 跟踪
（修好后那条复现转 exit 1 ⇒ 关账 + 收紧上界）。

## ④ 修法的正确性与风险（**先评估，不动手**）

⚠ **先纠正一个诱人的错答案**：把缓存键从 per-entry-closure 改成 per-module **不足以**
修好它，而且**已经试过一次并被正确性判红**。

### 4.1 已经证伪的那条路：平坦批编（T-C1…T-C5，2026-09-25）

做法：把模块根下**全部**文件当一个批次、共享一个环境编一次。结果两条都红：

1. **正确性** ✗（更严重）：课程单元的常态就是**重名**（每个 unit 自成一体、复用
   `mem_self`/`subset_mem`/`extra_*`）⇒ 平坦环境里后编单元**撞上**先编单元的同名声明 ⇒
   **假的"重复声明"错误**（真实形状上**必然**出现，不是偶发）。
2. **性能** ✗：真课程切片上批编 **11,491ms vs 逐入口 3,723ms（慢 3×）**——批里每个单元都在
   **更长的前缀**上工作。合成小单元项目里它反而 1.98× 快 ⇒ **合成负载会给出相反结论**。

⇒ 刹车（`docs/design/module-batch.md:159-165`）：CLI 接线撤掉、开关移除，只留惰性 API +
一条"已知限制"测试。**这条教训必须继承**：**共享 ≠ 合并环境**。

### 4.2 正解的形状（= 早已设计、从未实现的 K2）

`docs/design/closure-incremental.md:106-107`：per-module-root 的 **`ProjectSession`**——
一次编译、入口间共享 + 全局拓扑序 + **模块级**缓存（按内容哈希）。要点：

* **每个模块一个独立环境**（不是一个大平坦环境）⇒ 重名单元天然互不干扰；
* 入口 = 在**它自己的环境**里、按拓扑序**复用**依赖模块已经建好的环境 ⇒ 共享依赖**只编一次**；
* 需要的前端设施是 **环境快照/复用**（`EnvBuilder::with_env` / `snapshot`，T-K20′/T-K12c）——
  `crates/front` 今天**没有**这个入口（G-29 的根因：编译结束环境就没了）。

### 4.3 三个必须写清的失效/风险问题（错编比慢更严重）

| 问题 | 怎么防 |
|---|---|
| **依赖变了怎么失效** | 键必须是 **Merkle 链**：`key(模块) = H(自身源文本, prelude 模式, build stamp, 版本, 每个依赖的 key)`。依赖变 ⇒ 它的 key 变 ⇒ 所有下游 key 变（今天 per-entry 的 `digest` 已经是这个形状，只是**粒度错了**：把整条闭包折成一个键，而不是每个模块一个键）。**只按源文本哈希不够**（T-A06 的教训：入口路径必须进键，否则两个内容相同、位置不同的项目串台）。 |
| **部分失败怎么回滚** | 沿用既有纪律：**只缓存干净结果**（`store_if_clean*`，T-A05 已经把判据收成**一处**）；环境快照**只在整条闭包编译干净后**才允许提交进模块缓存；半成品**绝不入库**（宁可下次重编）。失败模块的下游必须重新走一遍"缺依赖"归因，不许复用上一次的环境。 |
| **会不会"该重编却没重编"（错编）** | 这是**红线**，判据必须**双向**：① **对拍**：冷编 vs 复用编，`--json` 事件流**逐字节相同**（含 `decl.checked`/诊断/计数）——整门课语料上跑，不是抽样；② **反向验证**：故意把依赖改一行 ⇒ 必须 miss（`crates/cli/tests/imports.rs` 已有这条，要**扩展到模块级**）；③ 把 `SOKO_SHADOW_CHECK` 那套**影子环境**对照（T-K12b）当作**过渡期**的独立裁判——注意它已实测**与内核阶段不等价**（偏严），所以只能当"报警器"，不能当判据。 |

### 4.4 收益上界与实测口径（等拍板）

* **上界**：4.14× 是"若每个模块只编一次"的**工作量上界**；但**闭包大小不预测耗时**
  （实测拟合 r=0.52、截距为负；闭包 5 的 unit06-solution 花 16.8s，闭包 8 的 unit12 只花 12.9s）
  ⇒ 省掉重复**只能省"依赖那一部分"**，而墙钟大头（**68% = 内核判定**）在入口自身
