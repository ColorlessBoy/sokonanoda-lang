编辑器体验：在 VS Code 里写证明

装完扩展，打开一个 .sokonanoda 文件就能写。目标状态、补全、期望类型、 诊断都由同一个完整内核给出；这一页把那些面板摊开，并给出每一块的复现命令。

§1 目标视图：内核的回答，不是编辑器的猜测

光标一动，扩展把位置发给语言服务器（自定义请求 soko/stateAt）。 服务器让完整内核算出当前的目标栈，编辑器只负责显示：binders 是假设， goal 是待证，goal_runs 与 ty_runs 是内核逐段的分类。

这一页的面板都是插图：真数据、静态 HTML，不能点，页面里也没有内核在跑。 每条 .illus-cap 都写了产生这份数据的命令。

  • P : Person -> Prop
  • Q : Person -> Prop
  • h : And ((x : Person) -> P x) ((x : Person) -> Q x)
  • x : Person

⊢

P x

这条状态来自 playground.sokonanoda 第 291 行第 3 列，也就是 apply And.left 那一行。内核一次给了两个子目标，面板就列两条。

同一份数据里的 checked 与 open 也不是形容词：它们是 query goals 的 status 字段原词。checked 表示内核真的收下了 这条证明，open 表示洞里还是 sorry。绿与朱在这里各自对应一次真实判定。

§2 编辑器窗口：状态栏的数字是内核数出来的

下面这个窗口是 playground.sokonanoda 的第 288–292 行，逐字照抄。 光标停在第 291 行——正是 §1 那个两目标状态的位置。

同一次运行还数出 example_checked 2 与 2 条 warning： reserved-declaration-name（第 84 行的 axiom Prop）和 redundant-sorry（第 333 行）。真状态栏只印一个数——未完成的练习数 4， 其余在 tooltip 里；这里的 30 checked 是按同一份真计数补上的，不是估的。

§3 补全与期望类型：把类型摆在手边

补全列表的四列都是真的：种类来自 CompletionItemKind，detail 是 crates/lsp/src/lib.rs:1372-1426 里那几串，签名是 query goals 的真 ty_runs。

内核按位置顺序把每个洞的类型对齐，编辑器把它贴在 sorry 的结束处， 形状就是 ": <期望类型>"（crates/lsp/src/inlay.rs:83）。 光标进洞之前，这行字就告诉你要证什么。

  • P : Person -> Prop
  • h : (x : Person) -> P x

⊢

Exists Person P

编辑器还会给下一步建议（textDocument/codeAction）：每个请求最多三条， 第一条带 is_preferred。标题由三条模板生成 （crates/lsp/src/actions.rs:104,131,147）： exact <假设>（用假设 <假设> 直接结束证明）、 refine <骨架>（按构造子拆分子目标）、 引入 <n> 个 binder（把证明写成 lambda 的第一步）。

限制

下一步建议这一页不画面板：scripts/soko query 没有暴露 codeAction，我拿不到可复现的输出。上面三串是源码里的模板， 不是渲染出来的界面。

§4 边写边诊断：波浪线下面是一次内核判定

诊断不是正则匹配。每条 diagnostic 都带一个 stage （parse / elab / kernel / import） 和一个稳定的 code，由完整内核给出；扩展把服务端的 publishDiagnostics 画成波浪线。

下面这条来自一行真的输入：def x : Nat := nosuchname。内核在 elab 阶段拒绝了 nosuchname 这个名字 （span 1:16-1:26）；代码区里同一个位置就是 .tok-err。

warning 不是诊断。redundant-sorry 只说这一行的 sorry 是多余的，它永不影响退出码，所以拿 --warn-* 而不是朱。

§5 四个视图：练习、课程、项目、目标面板

扩展在资源管理器里放三个树视图，第四个是右侧辅助侧栏里的 webview。 它们的 id、位置与生效条件都是 package.json 里的原值。

§6 命令与键位：14 条命令，5 个键位

下表是扩展贡献的全部 14 条命令。其中 5 条带键位，5 条在命令面板里隐藏—— 它们从视图标题栏或 code lens 出现，而不是让你去搜命令名。

计数命令：node -e 'const p=require("./editor/vscode/package.json"),c=p.contributes;console.log(c.commands.length,c.keybindings.length,Object.keys(c.configuration.properties).length)' → 14 5 3；注册处是 editor/vscode/extension.js 的 registerCommands()
命令 id键位作用
sokonanoda.showStatusalt+s列出当前文件的声明与状态，选中即跳到那一条
sokonanoda.status无同 showStatus；code lens 的目标，命令面板里隐藏

5 条键位都带 when: editorTextFocus && editorLangId == sokonanoda， 只在 .sokonanoda 文件里生效。命令面板隐藏的 5 条是 status、revealRange、goals.refresh、 courseRefresh、project.refresh。

另外 3 个设置：serverPath、serverOverride、 trace.server（把 LSP 流量写进输出面板）。前两个在受限工作区里被忽略， 受限模式总是用内置服务器。

§7 零工具链：LSP 与 CLI 都在扩展里

扩展自带语言服务器与命令行程序：VSIX 里就是 bin/<target>/sokonanoda-lsp 与 bin/<target>/sokonanoda， 覆盖 8 个平台（macOS arm64/x86_64、Linux gnu x64/arm64、Linux musl x64/arm64、 Windows x64/arm64）。装完打开文件就能写：不需要 Rust，不需要 Lean 或 elan， 也不需要联网下载。

服务端解析顺序是 bundled 优先：内置包存在即用，缺可执行位时自动补回。 只有没有内置包的平台（如 Linux armhf）才走版本锁定的下载缓存，而且钉到扩展自己的 release tag，从不取 latest。

serverPath、SOKONANODA_LSP_BIN 与工作区的 target/{debug,release} 默认被忽略，除非打开 serverOverride——这条默认值是为了防止旧构建静默覆盖内置服务器。 sokonanoda: doctor 会告诉你当前用的是哪一个。

§8 诚实的边界

限制

  • 这一页的面板是插图，不是活的编辑器：HTML 与 CSS 画的，数据来自真实录制输出 （每条 caption 都给了复现命令）。页面里没有内核，没有 WebAssembly， 也没有把你的输入送到任何地方。
  • 真 LSP 诊断通道不是每个 agent harness 都有。DeepSeek Harness 的 lsp 工具只有四个只读操作（跳定义、找引用、找实现、悬停）， 服务端的 publishDiagnostics 被显式丢弃 （packages/lsp/lsp-stdio/src/connection.ts:248）； 所以 agent 侧判卷一律走 CLI 的 --json 或 query， 别等编辑器诊断。
  • 与真面板的三处刻意差异：目标头在真面板是能跳转的 <button>， 这里是 <p>；真面板的声明行只有名字、种类与状态，插图里的 L288 是本页按 decl.start 的字节 offset 补的； 空态串末尾的勾号本站去掉（原因见 §1）。
