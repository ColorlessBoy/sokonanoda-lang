功能

给 code agent

这个项目把 code agent 当第一类用户：一条命令装环境，一份机器协议判卷， 判定永远来自内核。这一页写清 agent 能做什么、用什么命令、还不能做什么。

§1 一段可以粘进任何 code agent 的安装 prompt

下面这段是这一页的核心。它不内联任何细节：环境怎么准备、练习怎么出、 判定怎么读，全部委派给仓库里的 AGENTS.md 与三个技能正文。 这样 prompt 不会随着仓库演进而变成一句假话。

  • AGENTS.md : 仓库入口与 Setup
  • skills/ : 三个角色技能正文
  • playground.sokonanoda : 共享画布

⊢

一行由完整内核发出的判定

安装 prompt（粘给任何 code agent） 
请把 sokonanoda 安装为我的 Lean 4 式证明老师。按仓库里的文档做，不要凭记忆：

1. 拿仓库并进入目录：
   git clone https://github.com/ColorlessBoy/sokonanoda-lang
   cd sokonanoda-lang

2. 读 AGENTS.md，按它的 Setup 一节准备环境（在仓库根执行，harness 中立、零 cargo）：
   scripts/soko setup
   scripts/soko doctor --json
   "ready": true 才算就绪，退出码 3 表示没就绪。版本按仓库里的版本钉解析：
   禁用 releases/latest，不要安装 Rust，也不要碰官方 Lean 工具链
   （lean / lake / elan / leanc / lean4export）。

3. 读 skills/sokonanoda-teacher/SKILL.md，按它当老师：在 playground.sokonanoda 上
   出带 sorry 的练习，每道练习前挂 2-3 行 "-- soko:hint ..." 阶梯。
   DeepSeek Harness 会自动发现 .agents/skills/，技能名就是命令：/sokonanoda-teacher；
   其它 harness 直接读上面那个文件。改编译器读 skills/sokonanoda-dev/SKILL.md，
   推代码或查 CI 读 skills/sokonanoda-ci/SKILL.md。

4. 判卷只认内核，禁止文本比对：
   scripts/soko grade playground.sokonanoda --json
   scripts/soko query state --file playground.sokonanoda --line <行> --col <列>
   grade 给逐行 JSON 事件流；问「这个位置还差什么」用 query state 的单个 JSON 对象，
   不要自己扫事件流。DeepSeek Harness 里等不到 LSP 诊断，判卷一律走这两条命令。

先跑一次 grade，告诉我现在到哪了，再按我的进度推进。讲解与反馈用简体中文。

这段 prompt 里的每条命令都在仓库里核对过。它自己不带版本号， 版本由仓库的版本钉解析。

限制

这段 prompt 不承诺四件事：

  • 不承诺「VS Code 扩展自带二进制」这条兜底。scripts/soko 里有一个 extensionServer() 函数，但它从未被调用——文档写过这一环， 实现没有。实际解析链只有四步：显式 override、版本匹配的仓库构建、缓存、 按版本钉下载。
  • 不承诺 DeepSeek Harness 里会有 LSP 诊断。判卷一律走 CLI， 见 §6。
  • 不承诺零网络：第一次 setup 要下载版本锁定的 CLI 与 LSP。 离线时它明确报错并 exit 3，不会假装成功。
  • 不承诺在别的分支或旧检出上照跑：命令不变，但版本钉变了， 解析到的二进制就变了。

§2 三个角色技能

技能正文的唯一源是 skills/<name>/SKILL.md。 .agents/skills/ 里那五份是 DeepSeek Harness 的薄入口， 正文一行指回原处，两边的对应关系由 crates/cli/tests/dsh.rs 守住。

三个角色技能：给谁、什么时候加载、正文在哪。
技能 给谁 什么时候加载 正文
sokonanoda-teacher 当老师的 agent 用户想学 Lean 式证明、要判卷、要画布的当前状态 skills/sokonanoda-teacher/SKILL.md
sokonanoda-dev 接手开发的 agent 加语法、动编译器、动 CI 或文档 skills/sokonanoda-dev/SKILL.md
sokonanoda-ci 推代码与排错的 agent push、tag、release、GitHub Actions 红了 skills/sokonanoda-ci/SKILL.md

§2.1 加载它们的确切命令

三种 harness 三种写法，读到的正文是同一份： 

$ /sokonanoda-teacher                # DeepSeek Harness：技能名就是斜杠命令
$ ls .agents/skills/                 # 三个角色 + 两个人工运维入口
$ cat skills/sokonanoda-dev/SKILL.md # 任何 harness：正文是普通文件，直接读

$ 是提示符，不用输入。

  • DeepSeek Harness：自动发现 .agents/skills/， 技能名即命令（/sokonanoda-teacher、/sokonanoda-dev、 /sokonanoda-ci）。命令文法不允许斜杠，所以 opencode 的 /sokonanoda/update 在 DSH 侧只能写成 /sokonanoda-update。
  • opencode：opencode.json 的 skills.paths: ["./skills"] 启动即加载；另有 /sokonanoda/{setup,update,version,doctor,check,gate,round} 七个命令与 teacher 主 agent（Tab 切换）。
  • 其它 harness：没有自动发现，就把上面 cat 那行的路径 交给 agent 读。

另有两条运维技能 sokonanoda-update 与 sokonanoda-doctor： 它们带 disable-model-invocation，不进模型目录，是给人按的。 模型侧的等价能力已经写在 AGENTS.md 与三个角色技能里。

§3 机器协议：两个视图，同一份判卷

判卷有两个出口。grade --json 是逐行事件流， query <op> 是单个 JSON 对象；两者由同一次编译产出， 计数一致性由 crates/cli/tests/query.rs 钉死。

§3.1 grade --json：每行一个事件

stdout 上每行一个 JSON 对象，每行都带 type 与 human。 八种事件类型，字段只增不改：

八种 --json 事件：带了什么、什么时候发。
type 载荷 什么时候发
decl.checkedname声明通过了完整内核
example.checked—值位填好的 example 通过内核
expr.typedtext、inferred_type、span#check
expr.reducedtext、value、span#reduce
decl.printedname、text#print
exercise.openname（可缺）值位是 sorry 且签名合法的开放练习
warningcode、message、hint、span非致命 lint，永不影响退出码
diagnosticstage、code、message、hint、span任何错误

真实输出节选：第一条跑的是画布，第二条跑一份故意写坏的文件 （由 scripts/gen-site-lab.py 生成）。 

$ scripts/soko grade playground.sokonanoda --json
{"human":"checked declaration Prop","name":"Prop","type":"decl.checked"}
{"human":"exercise open (fill the sorry)","name":"forall_exists","type":"exercise.open"}

$ scripts/soko grade .cache/site-lab/repro/elab-unknown-identifier/main.sokonanoda --json
{"code":"elab-unknown-identifier","hint":"这个名字还没有被定义。检查拼写，或确认它出现在你前面的某个声明里（练习要在解决之后才能被后面的代码引用）。若它在该命名空间里，检查前缀或加 open。","message":"unknown identifier `nosuchname`","span":{"end":{"column":26,"line":1,"offset":25},"start":{"column":16,"line":1,"offset":15}},"stage":"elab","type":"diagnostic"}

$ 是提示符，不用输入。

内核真的通过过

上面第一条命令在本机对画布跑出 38 行事件： 30 条 decl.checked、2 条 example.checked、 4 条 exercise.open、2 条 warning、 0 条 diagnostic，退出码 0。 第二条命令对那份坏文件退出码 1，且只发一条诊断。

§3.2 query <op>：一次问一个问题

七个 op，每个回答一个具体问题。输入用 --file <path>、 --text <src> 或 stdin；--compact 打成一行。

七个 query op：要什么参数、回答什么。
op 需要什么 回答
check—计数、失败、告警（事件流的单对象摘要）
state--line L --col C 或 --offset N光标处的目标状态：decl、goal、binders、goals[]、step/total
goals可选 --probe每个声明的类型、状态、目标、洞
holes可选 --offset N --direction next|prev全部洞，带稳定 id <declName>:<index>
hints--line L --col C 或 --offset N该声明的 -- soko:hint 阶梯
reduce--expr E表达式在内核里的范式
project可选 --root <dir>项目闭包：根、清单、每个模块的状态

check 的完整输出可以很短——这是一份真文件、逐字未删： 

$ scripts/soko query check --file examples/lesson-01.sokonanoda --compact
{"data":{"counts":{"decl_checked":1,"decl_printed":0,"example_checked":0,"exercise_open":1,"expr_reduced":0,"expr_typed":1},"failed":[],"version":1,"warnings":[]},"ok":true,"op":"check","schema":"soko.query/1","version":1}

$ 是提示符，不用输入。

state 是这一族里最常用的一个。下面这份从真输出里摘出： 只去掉了给编辑器高亮用的 *_runs 数组与 start/end 偏移，剩下的字段与值逐字来自内核。 

$ scripts/soko query state --file playground.sokonanoda --line 280 --col 3
{"schema":"soko.query/1","op":"state","version":1,"ok":true,
 "data":{"decl":{"kind":"theorem","name":"forall_and","status":"checked"},
         "goal":"P x",
         "binders":[{"name":"P","ty":"Person -> Prop"},
                    {"name":"Q","ty":"Person -> Prop"},
                    {"name":"h","ty":"(x : Person) -> And (P x) (Q x)"},
                    {"name":"x","ty":"Person"}],
         "goals":[{"goal":"P x"},{"goal":"(x : Person) -> Q x"}],
         "step":1,"total":5}}

$ 是提示符，不用输入。

找不到答案时它不返回空结果，而是返回一个明确的错误码——ok:false 不是「这里没有东西」： 

$ scripts/soko query state --file playground.sokonanoda --line 1 --col 1 --compact
{"error":{"code":"outside-declarations","message":"该位置不在任何声明内部"},"ok":false,"op":"state","schema":"soko.query/1","version":1}

$ 是提示符，不用输入。

退出码：0 答上了（开放 sorry 是合法状态，上面那条 ok:false 也仍是 0）、1 文件被拒（内核拒绝、解析失败、 reduce 失败）、2 用法错误、3 环境或输入不可用。 判据看 JSON，不看退出码。

限制

「同一份真相」有一个已知例外。文件如果用到了从 import 模块继承来的记法，query check 会报一条 grade 没有的失败：入口先按单文件解析（拿不到继承来的记法表）， 报 notation-unknown-symbol；随后项目层正确改判为项目并闭包重编 （计数证明重编跑过了），但第一次的解析诊断留在了 failed[] 里。 实测同一个文件、同一个二进制：query check 退出码 1 且 failed[0] 落在第 96 行第 42 列，而 grade --json 退出码 0、24 条事件、0 条诊断。自己声明的记法与 import 来的名字都不受影响， 只有继承来的记法会。 要验证这类文件，用 grade --json，不要用 query check；mcp__sokonanoda__check 走的是同一条通道，会继承同一个假红。

版本标注：这条属于当前发布版本。未发布的下一批改动里 它已不再复现（同一条命令、同一个文件，工作区构建退出 0、failed: []）—— 发布之后请重测。本站写的是已发布版本的事实。

§3.3 问「这里还差什么」为什么用 query state

事件流是按「发生了什么」排列的，不是按「你在哪」。它没有「当前位置的目标」 这个概念：decl.checked 与 exercise.open 只带名字， 连目标文本都没有。要从事件流回答「这个位置还差什么」，你得先按 span 过滤、找到所在声明，再从几条事件反推——而反推需要的信息它根本没打印。

query state 直接把光标位置交给内核，让它算出该位置的目标栈 （Lean 的 goalsAt? 语义），一次返回 decl、 goal、binders、goals[] 与进度 step/total。三种问法各有其 op：

  • 「某处还差什么」用 query state
  • 「哪个模块拖坏了入口」用 query project
  • 「洞在哪、下一个洞是哪个」用 query holes
  • pos : 光标位置
  • sorry : 一个未解的洞

§4 工具面：MCP 七个工具与 soko/* 六个请求

§3 那七个 op 还有两条给机器用的包装：MCP 那条给模型直接调用， soko/* 那条是 LSP 自定义请求，给编辑器用。

§4.1 MCP 七个工具

scripts/soko mcp 起一个 stdio server （dsh/mcp/server.js，零依赖的 JSON 转发器，不含任何 Lean 逻辑）， DeepSeek Harness 把它暴露成 mcp__sokonanoda__<名字>。 有工具就直接调，别绕 shell。

七个 MCP 工具：转发到哪个 op、关键参数是什么。
工具名（DSH 里看到的） 转发到 关键参数
mcp__sokonanoda__checkquery checkfile?、text?
mcp__sokonanoda__statequery statefile/text、line、character（1-based UTF-16）
mcp__sokonanoda__goalsquery goalsfile/text、probe?
mcp__sokonanoda__holesquery holesfile/text、offset?、direction?
mcp__sokonanoda__hintsquery hintsfile/text、line、character
mcp__sokonanoda__projectquery projectfile/text、root?
mcp__sokonanoda__reducequery reduceexpr（必填）

实测：这个 server 的 tools/list 正好 7 个工具，serverInfo 报 sokonanoda。它在 DSH 里默认关闭，要显式 dsh web --patch ./dsh/cordis.patch.yml 才生效；多文件项目走 file: 而不是 text:，因为 import 的解析 需要真实路径。

§4.2 soko/* 自定义 LSP 请求

编辑器侧的六个自定义请求。它们与 query 是两套通道， 契约都在 docs/protocol.md。

六个 soko/* 请求：参数与返回要点。
请求 参数 返回要点
soko/goals{textDocument, position}每个声明的 name、kind、status、range、ty、goal、goals、binders、hole、holes[]、sub_goals
soko/hints{textDocument, position}{hints: [string]}，来自 -- soko:hint 阶梯；服务端无状态
soko/stateAt{textDocument, position}{version, decl, goal, goal_runs, binders, goals[], span, step, total}
soko/project{textDocument}{uri, version, project{entry, root, manifest, requires_warning, modules[], diagnostics[], counts}, reason}
soko/version{}{version, pid}，服务器自述，重启命令用
soko/nextHole{textDocument, position, forward}null 或下一个洞的 range

消费者只有 VS Code 扩展与 opencode。DeepSeek Harness 侧目前没有消费者， 见 §6。

§5 硬规则

下面四条不是风格建议，是判据。违反它们的 agent 会给出与内核相反的结论。

  1. 判定永远走内核，禁止文本比对。读 --json 事件或 query 的单对象回答：decl.checked 是通过、 diagnostic 是失败、warning 永不影响退出码。 「看起来对」不是判据。
  2. exercise.open 是合法状态，不是错误。 它的含义精确：值位是 sorry，且签名已经 elaborate 通过。 它照样让退出码是 0。反过来不成立——签名 elaborate 不了、不是一个类型、 或 theorem 的签名不是 Prop，都变成一条 diagnostic 且声明 Failed，不发 exercise.open。所以别拿 exercise.open 的计数 当「签名没坏」的证据，要看 diagnostic。
  3. 版本钉死，禁用 releases/latest。 下载 URL 一律带 v${version}。用 latest 会让 新服务器配上旧客户端，soko/* 协议静默漂移——历史上真发生过。 启动器只在解析出完整 x.y.z 时才下载，纯约束（如 0.58）会被明确拒绝并说明没有对应的 release tag。
  4. 不安装、也不调用官方 Lean 工具链。lean、 lake、lean4export、leanc、 elan 一律不用：这个内核是自研的。opencode 由 opencode.json 的 permission deny 强制；DSH 侧要用户往 profile 插一行 hooks，没插就只是文档纪律（见 §6）。

还有一条环境规则：用户与 agent 的路径零 cargo。 不为了使用而安装 Rust；Release tarball 里就是可直接执行的二进制， VSIX 平台包里内嵌 LSP 与 CLI。只有贡献者跑 cargo。

  • rules : 四条硬规则
  • exit : 一次判卷的退出码

§6 现在还不能做什么

限制

这一节是这一页最该被读的部分。下面每一条都有源码或实测撑着， 没有一条是「以后会好」的许诺。写页面时不软化它们，是因为一个会 白等 LSP 诊断的 agent 比一个知道要走 CLI 的 agent 贵得多。

按 harness 列出：现在还不能做什么、凭什么这么说。
harness 现在还不能 凭什么这么说
DeepSeek Harness 内核诊断不会进 agent 上下文，也不会进 Web UI 服务端 publishDiagnostics 被 LSP host 显式忽略；判卷一律走 CLI --json
DeepSeek Harness lsp 工具只有四个只读操作：goToDefinition、findReferences、goToImplementation、hover soko/goals、soko/stateAt、soko/nextHole、soko/hints、inlay hints、code action、semantic tokens 在 DSH 侧全部无消费者
DeepSeek Harness LSP 不是开箱能力，必须显式挂载；lsp 工具只认会话工作区内的文件 LSP 不在任何 shipped bundle 里，要 dsh web --patch ./dsh/cordis.patch.yml；工作区必须是本仓库根
DeepSeek Harness 不能靠 PATH 找到 sokonanoda 工具调用的 PATH 不允许被项目配置；所有命令只能写显式路径 scripts/soko（这正是文档一律用启动器形式的原因）
DeepSeek Harness Lean 工具链禁令不是配置强制的 DSH 没有命令黑名单；仓库自带 hooks，但要在用户 profile 里插一行指向它，否则退回文档纪律
DeepSeek Harness 没有项目级启动钩子，首次使用多一步人工 patch 只能由用户显式 --patch 或写进 profile；要人工跑一次 scripts/soko setup。反面是好事：不会启动即联网
DeepSeek Harness MCP 七个工具默认不可用 MCP server 是 DSH 沙箱之外的可信可执行代码，所以默认关闭，要那行 --patch 才生效
DeepSeek Harness opencode 的七个 /sokonanoda/* 命令不存在 DSH 的人类命令必须由插件注册；可用的是技能名本身（/sokonanoda-teacher 等）
opencode 启动插件只在 opencode 启动时生效 其它 harness 没有等价物；通用退路是 shim .opencode/lsp/sokonanoda-lsp.sh 与显式路径
所有 harness 不能指望「VS Code 扩展自带二进制」这条兜底 scripts/soko 里的 extensionServer() 从未被调用，是死代码；解析链实际只有四步。opencode 插件倒是真的实现了这一环
所有 harness 用到 import 来的记法的文件，query check 会报假红 同一个文件、同一个二进制：query check 退出码 1，grade --json 退出码 0 且 0 条诊断。MCP 的 check 继承同一个假红（详见 §3.2）。 版本标注：属当前发布版本；未发布的下一批已不再复现，发布后请重测
所有 harness soko/nextHole 只能按组跳，不能按目标跳 一个 apply 的两个子目标共享同一个源位置；程序化消费的稳定引用是 holes[i].id，不是位置

远期 backlog 里还挂着几件不做承诺的事：DSH 客户端插件复刻目标面板、 SessionStart 钩子自动 setup、把 DSH 侧打包成一个 npm 插件。它们没有排期，也不该被当成「快有了」。
