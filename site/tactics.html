§3

策略与证明

写证明有两种写法：by 块里的 tactic，和直接写一个证明项。 这一页把两种写法的全部词汇列完——by 块只有七个 tactic，一个不多。

§1 by 块不是第二套语义

一个 by 块进内核之前会被降级成一个 lambda （crates/front/src/by.rs）。intro a 变成一层 fun (a : …) => …，exact e 变成那个位置的项， apply f 变成 f 带上若干还没填的实参。所以 by 块不引入新的类型规则，它只是替你写项。

判定同样不走捷径：by 引擎把「声明类型 + 已引入的 binder + 当前剩余目标」 折回一个完整的声明，交给完整内核裁决 （front::judge，crates/front/src/judge.rs）。 内核说通过，这一条才 checked。整个过程里 没有任何一处把 tactic 文本和什么东西做字符串比对。

  • a : Prop
  • b : Prop
  • ha : a
  • hb : b

⊢

And a b

上面这个状态，就是下面 apply And.intro 那一步的进入状态： 假设在上，待证在横线之下。本页每个 tactic 都配一张这样的面板， 面板里的每个字都来自内核，命令写在图注里，可以照着复现。

§2 白名单：七个 tactic，一个不多

白名单由 crates/front/src/parser.rs 的 is_tactic_keyword 与 parse_tactic_inner 的 match 臂共用同一个集合——两处不可能漂移。 里面的 match 被解析成 Tactic::Exact，所以 crates/front/src/ast.rs 的 enum Tactic 只有六个变体。

已发布版本里 by 块接受的全部写法。第四列是本页对应的小节。
写法 它对目标做什么 源码出处 例子
intro x 剥掉目标最外面一层箭头，把那个假设按名字 x 收进上下文 ast.rs Intro §2.1
exact e 用项 e 直接结束当前目标；类型对不对由内核判 ast.rs Exact §2.2
apply f 目标套上 f：f : A1 -> … -> An -> 目标 时，目标换成 A1..An 个子目标 ast.rs Apply §2.3
assumption 在当前上下文里找一个类型与目标一致的假设，直接用它 ast.rs Assumption §2.4
rfl 目标是 Eq 且两边算出来是同一个值时成立 ast.rs Rfl §2.5
match 臂体是项；语义等价于 exact (match … with …)，期望类型就是当前目标 parser.rs 解析成 Exact §2.6
sorry 什么都不做：当前目标保持开放，声明成为合法的未完成状态 ast.rs Sorry §2.7

tactic 之间用 ; 或换行分隔。下面每个小节的例子 都来自同一份文件，可以用一条命令整份判卷。

§2.1 intro x：把箭头拆成假设

目标最外面是一层箭头时，intro x 把它剥掉，把左边那个前提按 名字 x 收进上下文。它等价于在证明项最外面写一层 fun (x : …) => …。名字可以一次写多个 （intro a b c 是三层），语义就是连写三次。

§2.2 exact e：交一个项，结束当前目标

exact e 把当前目标关掉，条件是 e 的类型与目标一致。 「一致」由内核判：它会把 e 放进一个合成声明里真的检查一遍， 算不算得出来、宇宙层级对不对，都由内核说了算。

上面 apply And.intro 那一步把目标 And a b 换成了 两个子目标，所以后面要两条 exact：第 12 行的 exact ha 收掉 ⊢ a，第 13 行的 exact hb 收掉 ⊢ b。子目标按产生顺序排队。

§2.3 apply f：把目标换成前提

apply f 要 f 的结论正好是当前目标； 它把目标换成 f 需要的那几个前提。这是「倒着证」： 从结论出发，找一条能推出它的规则。

§2.4 assumption：在上下文里找答案

目标恰好就是某条假设时，assumption 替你把它找出来并交上去。 它不接受参数——找哪一条由内核决定，不是由文本相似度决定。 这也是 intro 之后最常见的一步。

限制

assumption 只找类型与目标一致的假设。 它不做传递推理，也不做任何简化：上下文里只有 h : And a b 而目标是 a 时它帮不上忙—— 那种情况要先用 apply And.left 把目标拆开，或者直接 exact And.left a b h。

§2.5 rfl：两边算出来一样

目标是 Eq 时，rfl 让内核把两边各自算到 规范形式再比。它证明的是「这两个写法是同一个值」，不是「这两个写法长得一样」—— 1 + 1 与 2 在源码里是两串字符，在内核里是同一个自然数。

请注意

这条例子的类型写作 Eq.{1} Nat (1 + 1) 2，宇宙层级必须显式写。 写成 Eq Nat (1 + 1) 2 时 rfl 会失败并报 「期望 Sort(0)，实际 Sort(1)」—— by 引擎合成的判定声明不带宇宙参数，这是当前版本的已知边界。 课程里同一条也写作 Eq.{1}（course/unit4-by-tactics.sokonanoda）。

§2.6 match：臂体是项

by 块里的 match 与值位的 match 是同一个东西， 语义等价于 exact (match … with …)：臂体是项， 不是一串 tactic。期望类型就是当前目标，内核拿它当 motive 去推。 解析器把 by match … 直接读成 Tactic::Exact， 所以它没有自己的类型规则。

限制

本页所有其他 tactic 都能给出一进一出两张目标面板；match 只给得出「走完」。 原因是 query state 按光标位置选步：光标落在某条 tactic 的 起始字节之前时它给根状态，落在之后时给最后一步之后的状态， 而 match 是整块一步、没有中间步可停。所以上面这张面板的 「进入状态」只能从声明类型读出来，写在这里而不是画成面板。

这门语言的 match 有四条限制，都在 docs/design/match-patterns.md 里：没有元组/记录/字符串字面量模式； 参数化归纳的被匹配项必须是写成 T 参数… 的局部变量； 依赖索引的结果类型不在 v1；递归归纳类型要用消去子 .rec， 不能用 match。上面这个 Color 是非递归的，所以能过。

§2.7 sorry：合法地留空

sorry 什么都不做：当前目标保持开放，声明成为 exercise.open。这不是错误——判卷退出码仍是 0， 编辑器把这一条显示为「还没解」，而不是「写错了」。 课程里的练习起点就是这个状态。

限制

sorry 只能出现在声明的值位或 by 块里。 写在别处报 elab-hole-misplaced；??? 这种洞 已于 2026-09-07 移除，今天不是语法。

§3 不用 tactic 的写法：证明就是项

by 块是方便写法，不是必需品。课程的主线恰恰相反： 先教「证明 = 构造项」，再教 tactic 只是替你写那个项。 下面八条都是普通值位写法，全部通过内核。

项级证明构造。第二列的类型由 query goals 给出（内核 pp 的原话）。
构造 源码 内核给出的类型
lambda fun (a : Prop) => fun (h : a) => h forall (a : Prop), a -> a
应用 And.left a b x forall (a b : Prop), And a b -> a
构造子 And.intro b a (And.right a b x) (And.left a b x) forall (a b : Prop), And a b -> And b a
消去子 False.rec a h False -> (forall (a : Prop), a)
等式自反 Eq.refl.{1} Nat 1 Eq 1 1
等式替换 Eq.subst.{1} Prop (fun (x : Prop) => x) a b h ha forall (a b : Prop), Eq a b -> a -> b
let let m : Nat := n + 2; m Nat -> Nat
match 作为项 match c with | red => green | green => red Color -> Color
内核替你算 Eq.refl.{1} Nat 2 Eq (Nat.add 1 1) 2

Nat.rec 也在语言里。它的类型是 Nat.rec.{u} (motive : Nat -> Sort u) : motive Nat.zero -> (forall (n_ : Nat), motive n_ -> motive (Nat.succ n_)) -> (forall (target : Nat), motive target) （#print Nat.rec 的原话），实参顺序就是 motive、零的那一支、 后继的那一支、被消去的数。它和 False.rec 是同一类东西： 归纳类型自带的消去子。递归归纳类型不能用 match，要用它—— 课程里 double 与 add 都是这么写的 （course/solutions/unit6-induction-recursion-1-solution.sokonanoda）。

  • a : Prop
  • x : And a b

⊢

And b a

同一个目标，两种写法：by 块里写 apply And.intro 再两条 exact， 或者直接交 And.intro b a (And.right a b x) (And.left a b x)。 前者会被降级成后者，然后一起进内核。

§4 故意没有的 tactic

simp、rw、constructor、cases、 induction、omega、norm_num、 exact?——都没有。写下去会拿到一条 parse 阶段的 unexpected-token，消息里点名全部七个合法写法。

请注意

白名单外的名字出现在 by 块第一句时，报的是通用消息 expected a .sokonanoda command, found Token { … Ident("simp") … }， 而不是上面那条点名七个写法的消息。两条都真跑过。本页用后者，因为它把白名单 本身写进了错误里。

§4.1 为什么是关上的

加一个 tactic 不是加一个函数。按仓库的硬规则 3，新增语法要 三件套一起交：课程内容、测试、白名单。加 cases 意味着要有一课讲清楚它什么时候用、什么时候会把目标拆坏， 要有一组测试钉住它在依赖 motive 下的行为，还要在 is_tactic_keyword 与 parse_tactic_inner 两处同步。 这三件事的课程与测试成本才是真正的门槛。

还有一条更硬的理由：每个新 tactic 都要能在内核里说清楚它做了什么。 intro 是 fun，exact 是项， apply 是应用——都能一对一地降级成项。 simp 与 omega 不是：它们各自带一套重写或判定过程， 要解释清楚就得引入新的判定语义，而内核是冻结的。

最后是教学顺序。白名单里的七个刚好覆盖「拆前提、交答案、倒着推、找现成的、 算等式、分情况、留空」这七件事；一门 11 个单元 + 卷 I 12 个单元的课， 用这七件事已经能写出卷 I 里 329 条通过的内核判定。

§5 七个 tactic 与它们手写的等价项

  • by intro a
  • by apply And.intro
  • by exact ha

⊢

fun (a : Prop) => And.intro … ha …

左边是 by 块的写法，右边是它降级之后的样子。 最后一列是内核实际看到的东西——同一份声明，两种写法只差在谁替你写项。

降级对照表。第二列的项写法都直接通过内核；第一列的 by 写法先降级成第二列。
tactic 降级成的项（同一目标下） 内核看到的目标
intro a fun (a : …) => … 少一层箭头，多一条假设
exact e 就是 e 这个目标消失
apply f f 应用于若干待填实参 1 个目标换成 n 个
assumption 上下文里那条类型一致的假设 这个目标消失
rfl Eq.refl 那一族 这个目标消失
match match … with … 整个项 这个目标消失
sorry 一个洞（保持开放） 目标原样留着

§6 这份白名单是约束，不是遗漏

限制

白名单是关上的，这是设计决定。它一共七个，两处源码共用一个集合， 加一个就要同时改课程、测试、白名单三处——所以「Lean 里能用的 tactic 这里也能用」 这句话在本语言里不成立。加 tactic 是语言变更， 要另立一轮课程与测试，不是改一个名字的事。

这条约束有两个可以直接检验的后果。一是不可迁移的写法会当场报错， 不会静默地「差一点」：simp 与 omega 都拿到 parse 阶段的 unexpected-token， 消息里点名七个合法写法。二是能写出来的证明一定有一个项级的对应物—— 因为每个 tactic 都要能降级成项。这也是为什么 simp 这类自带判定过程的 tactic 不会先进来： 它们说不清降级成哪个项。

如果你在别处学过 Lean 4，需要调整的是手而不是理解： 把 rw 换成 exact 加 Eq.subst， 把 constructor 换成 apply And.intro， 把 cases 换成 match 或消去子 .rec。 每一步都更啰嗦，但每一步都能被内核逐个检查。

本页没有一条例子依赖工作区里的未提交改动。所有目标状态、错误消息与计数 都由已发布版本的二进制产生，命令写在每张图的图注里。
