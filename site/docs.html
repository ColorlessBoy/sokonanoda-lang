使用

文档索引

仓库里的文档分三层，一共 88 份。这一页是那张地图： 哪份先读、每份解决什么问题、什么时候才需要它。正文一个字都不搬过来—— 点开就是仓库里的原文。

§1 先读这三份

面对 88 份文档，唯一有用的信息是顺序。下面三份是任何身份都先读的： 它们给定位、给硬规则、给现状。读完这三份，再按 §6 里你那一行往下走。

  1. README.md —— 对外门面：这是什么、三条使用路径、怎么装上。
  2. AGENTS.md —— 项目入口：阅读顺序、六条硬规则速记、全部命令。任何 code agent 从这里进。
  3. STATUS.md —— 当前进度与逐轮日志（最新一轮在最上）。先知道现在在哪，再决定读什么。
  • 给定：接手这个仓库
  • 顺序：README → AGENTS → STATUS

⊢

目标：知道下一份该读哪一份

AGENTS.md 自己给的是完整顺序，五步： REQUIREMENTS.md → docs/HANDOVER.md → STATUS.md → ROADMAP.md §10 → docs/architecture.md（§8 必读）。 skills/sokonanoda-dev/SKILL.md 写得更细（七步，多出 docs/README.md）—— 两处是同一份清单的两个粒度，§6 的「代码 agent」一行是合并后的版本。

§2 这一页站在哪

这个站点是仓库的一个视图，不是第四个真相源。文档原文、设计决策、 失败记录全部留在仓库里，站点只做两件事：把生成好的数据渲染出来，把路径指给你。 这条边界是刻意的——仓库里的东西跟着 commit 走，站点不会。

限制

站点与仓库之间存在时间差，而且消不掉。站点的计数、版本号、时间线由 scripts/gen-site-data.py 生成一次、写进 site/data/site.json， 之后不再自动跟随。所以别处页面上的数字是某次生成的快照， 仓库里的文档永远比它新。要判断某个说法是否还成立，读仓库里那一份，不要读转述。

对应关系是：站点的一页讲一件事，仓库的一份文档负责那件事的全部细节。 本页能做的是把「哪份文档讲什么」和「什么时候才需要它」对上。 下面三节就是仓库自己的三层结构，逐层列出。
