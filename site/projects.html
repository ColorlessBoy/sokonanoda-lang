功能

多文件项目：模块、清单与闭包编译

一个文件里出现第一行 import，编译单元就从「这一个文件」变成 「入口加它的 import 闭包」。这一页把这条路径摊开：模块名怎么来、根在哪、 一个模块坏了会怎样，以及编辑器和 agent 分别从哪里看项目的状态。

§1 模型：模块名就是路径

没有 import 的文件走单文件路径，而且从不读清单—— 祖先目录里的 sokonanoda.toml 再坏也与它无关。这是契约，不是实现巧合： crates/cli/tests/single_file_vs_project.rs 用四条测试把它钉住。

出现 import 之后，闭包的形状由三条规则决定，三条都取自官方 Lean 4。

  • 模块名 = 相对模块根的路径。 lib/Set.sokonanoda 就是 lib.Set；分隔符只写 .，路径里的 / 由编译器补。大小写敏感。 - 不是模块名字符，所以 unit1-propositions-proofs.sokonanoda 这类文件不可被 import—— 编译器给的是 import-not-a-valid-module-name，而不是一句「找不到」。
  • import 必须写在所有声明之前。 写在声明后面就是 import-must-precede-declarations， span 精确到那一行。
  • 模块根由最近的 sokonanoda.toml 决定。 从入口文件所在目录向上找；走到含 .git 的目录、或走到 $HOME，就停下不再往外找。找不到清单也有退路：模块根 = 入口文件所在目录。
  • import lib.Set
  • root = courses/set-theory

⊢

courses/set-theory/lib/Set.sokonanoda

§1.1 根从哪来：五种情形，逐条实测

上例的 root 不是猜的：courses/set-theory/sokonanoda.toml 存在，所以它是根。优先级是「--root 显式指定 > 最近的清单 > 入口文件所在目录」；--no-project 把第二条整条跳过。 下表每一行的 root 与 manifest 都是 query project 真答出来的字段值。

五条命令的实测结果。零配置两文件项目放在 .cache/nomanifest/（只有 A.sokonanoda 与 B.sokonanoda，没有清单）；其余四行跑在 courses/set-theory/ 的一份副本上
你怎么调 模块根 root 生效清单 manifest
入口没有 import 不适用（走单文件流水线） 不读；答案是 project: null + reason: "no-imports"
有 import，祖先目录里有清单 …/courses/set-theory …/courses/set-theory/sokonanoda.toml
有 import，没有清单 …/.cache/nomanifest（入口文件所在目录） null——零配置，不是错误
有 import + --root <dir> 你给的那个目录，清单发现被整条跳过 null：即使那个目录里有清单，也不再读
有 import + --no-project 入口文件所在目录 null；import lib.Logic 于是解析到 <入口目录>/lib/Logic.sokonanoda，报 import-not-found

请注意

--root 与 --no-project 只对有 import 的文件生效。 单文件下它们是空操作——没有闭包，也就没有根可覆盖。

§2 一个真项目：卷 I《集合论》

仓库里最大的一个真项目是课程卷 I：courses/set-theory/。 它不是两文件的演示——9 个库模块、12 个单元、1 份清单， 单元靠 import 复用库，库与库之间自己也有依赖。

§2.1 清单：四行，其中两行是注释

courses/set-theory/sokonanoda.toml（逐字全文） 
# 卷 I《集合论》—— 模块根 = 本目录（与将来的独立课程仓同构）。
# 语言仓测试/脚本一律用**绝对路径**判卷（台账 G-12：相对路径 + 祖先清单会让模块根退化）。
name = "set-theory"
requires = "0.61"

清单的存在就是信息：这个目录是模块根。 name 只是元数据，不参与解析；requires 是工具链意图 （major.minor 匹配），不匹配时给一条 warning 落在 query project 的 requires_warning 字段里，不阻断编译。 三个键全都可以不写，空文件也是合法的根标记。

§2.3 单元怎么用库：12 个单元，闭包 3 到 8 个模块

单元文件开头只有两行 import，其余全是练习。 单元②的 import 写在所有声明之前——位置是 units/unit02-subsets-empty.sokonanoda:10-11：

courses/set-theory/units/unit02-subsets-empty.sokonanoda:10-11 
import lib.Logic
import lib.Set

import 没有 open 语义： 库里的 Set.subset 进来就叫 Set.subset， 想写短名得自己 open Set（或让库 export）。 这不是遗漏，是官方 Lean 的规则：导入改变「名字从哪来」，不改变「短名可见不可见」。

§3 闭包编译：一个模块坏了会怎样

这是项目模式里最值得单独讲的一条规则，因为它的表现和直觉相反： 你在库文件里写错一个标识符，诊断却出现在用它的那个文件的 import 行上。

做法是把 courses/set-theory/ 复制一份，只动一行： lib/Set.sokonanoda:98 的 True.intro 改成 True.intro2，然后照常判卷入口 units/unit02-subsets-empty.sokonanoda。

  • lib/Set.sokonanoda:98 有一条内核拒绝
  • units/unit02-subsets-empty.sokonanoda:11 写着 import lib.Set

⊢

入口只在 11:1 收到一条 import-dependency-failed

规则是失败即阻断：一个模块有解析或检查失败， 所有 import 它的模块不编译，只在各自的 import 行上报 一条 import-dependency-failed，指向上游的第一条错误。 不这么做的话，下游会级联出几十条「未定义标识符」，把真正的第一因埋掉。 而依赖自己的那条错误不会被吞：它带着 file 与 module 字段原样留在事件流里，编辑器据此把波浪线画在库文件的那一行上。

query project 里 status 只有三个取值。第三列是上面两次实验里的实测落点
status 什么时候是它 两次实验里谁是这个状态 它自己的错误落在哪
compiled 编译器走完了这个模块（走完不等于没错） lib.Logic；实验一的 lib.Set（decls 23、errors 1） 它自己文件里的那一行
load-failed 加载期就失败：文件缺失、解析失败、成环 实验二的 lib.Set（decls 0——一条声明都没进环境） 它自己文件里的那一行
blocked 上游失败，没轮到它编译 两次实验里的入口 units.unit02-subsets-empty 只在入口的 import 行上，一条 import-dependency-failed

实验一的 counts 是 {modules: 3, compiled: 2, failed: 0, blocked: 1, decls: 23, errors: 2}； 实验二是 {modules: 3, compiled: 1, failed: 1, blocked: 1, decls: 0, errors: 2}。 注意 failed 数的是 load-failed，不是「有错误的模块」—— 所以实验一的 failed 是 0，而 errors 是 2。

第三种失败是根本找不到文件。把 import lib.Nope 写进一个只有清单的目录，回答是 import-not-found， 消息里直接给出期望的完整路径 （…/lib/Nope.sokonanoda），不让你猜根在哪。 环（import-cycle）走同一条路：报出环的路径，整个闭包一起停。

§4 项目视图：根、清单来源、每模块状态

闭包状态只有一份真相层（front::query::project_view）， 两个传输：CLI 的 query project 给脚本与 agent， LSP 的 soko/project 给编辑器。两边字段同名同义， 都由同一次已经编译过的闭包派生，不重跑内核。

同一个答案在 CLI 里是一个 JSON 对象，信封是 soko.query/1。 单文件不是错误，是另一种合法状态——用 project: null 加一个机器码表达：

{"data":{"project":null,"reason":"no-imports"},"ok":true,"op":"project","schema":"soko.query/1","version":1}

逐字来自 scripts/soko query project --file playground.sokonanoda --compact， 退出码 0。reason 还有两个取值：no-path（stdin 或未保存的新文件， 有 import 却没有入口路径）与 parse-error（先修语法）。

编辑器侧走自定义请求 soko/project，请求体是 {textDocument: {uri}}，应答回显 uri 与 version—— 扩展据此丢弃「答的是另一份文档」的过期答案。视图 id 是 sokonanoda.project（when: resourceLangId == sokonanoda）， 标题栏的刷新命令是 sokonanoda.project.refresh。 改一个被 import 的库文件时，服务器重编译下游并推新诊断，树跟着更新。

§5 与其他语言的对照

这一节的出处是仓库里一份对十个系统的逐条考证 （docs/notes/multifile-prior-art.md，事实都对着官方文档核过）。 只看三个问题：检查一个文件需不需要清单、 模块身份是路径还是声明、产物靠什么失效。 这三个答案决定了「打开一个文件要几秒钟才能开始写」。

十个系统的模块与项目规则，以及本项目逐条的取舍。考证见 docs/notes/multifile-prior-art.md，取舍见 docs/design/imports-and-projects.md §2.5
系统 裸文件能跑吗 模块身份 产物靠什么失效 本项目取了哪一半
Rocq 能：rocq c foo.v 推导：-Q/-R 的逻辑路径加文件名 .vo 放在源码旁，比源码旧就重编 取「推导」与「向上找清单」；不取命令行映射
Agda 能：agda Foo.agda 推导，且严格 name == path .agdai 放源码旁或 _build/VERSION/ 取严格对应；不取「改名后留下孤儿接口文件」
Isabelle 不能：没有单文件模式 声明的 theory 名，文件名只是惯例 heap、日志、构建库放 ISABELLE_HEAPS 不取——「检查一个文件要先有 session」正是要避开的反例
Idris 2 能：idris2 f.idr 声明 module Foo.Bar，且必须与路径一致 build/ttc/*.ttc，源文件变了就重生成 不取声明：同一个名字写两处就会漂
Rust / Cargo 能：rustc f.rs 声明 mod 加固定文件规则 target/，主要靠文件时间戳 取祖先找清单；不取时间戳，本项目按内容哈希
Go 能：go run f.go 不需要 go.mod 包路径 = 模块路径加目录 GOCACHE；可执行文件写在源码旁 取「包路径 = 模块路径 + 目录」，正是 lib.Set 的形状
Python 能，而且根本没有清单 从文件名推导，从不声明 __pycache__ 放源码旁，按源文件 mtime 取推导；不取「首次命中即胜」的静默歧义
Node / TypeScript 能：node script.js CommonJS 没有模块名；ESM 的 specifier 就是路径 node_modules；outDir 与 .tsbuildinfo 取「最近的父清单」；不取隐式 node_modules 上溯
GHC / Cabal 能：ghc hello.hs 声明，且文件必须正好在 A/B/C.hs .o/.hi 放源码旁，靠 mtime 加 MD5 指纹 取指纹思路（本项目的键是闭包内容）；不取「必须逐个列出模块」
OCaml / Dune ocaml f.ml 能跑，但 Dune 没有 dune-project 就拒绝工作 推导，从不声明 _build/default；.cmi/.cmx 取「推导加从不声明」；不取「没有清单就不工作」
JVM / Maven 能：java Hello.java 声明 package 加类型名，目录规则由宿主决定 .class 放源码旁或 -d/target/；最新的文件胜 取「裸文件能跑」；不取「目录规则可有可无」

三个结论直接落成了本项目的规则。其一，只有 Isabelle 不接受裸文件， 而初学者最先遇到的语言全都接受——所以单文件是默认，项目是 opt-in。 其二，只有 OCaml 与 Python 完全不声明模块身份， Rocq 与 Go 从路径加根推导，Haskell、Idris、Isabelle 要求声明并校验—— 本项目选推导：一个文件一个规范名，没有第二处要同步。 其三，没有一处靠时间戳就够：GHC 是 mtime 加指纹，Go 是构建缓存， Cargo 自己承认「主要靠时间戳」。本项目的键是闭包内容， 所以改了被 import 的文件，所有下游必然重编，注释改一个字也算。

§6 诚实的边界

项目模式（import、清单、闭包编译）是 2026-09-18 落地的那一批。 它有明确的边界，全部登记在设计与台账里，下面五条是其中会被你撞到的。

限制

  • 项目模式没有跨模块增量。一次编译是一个 arena 加一个环境构建器， 改一个库文件就是整个闭包重编。视图也不承诺「哪个模块没重编译」—— 「跨进程的模块级缓存」在设计文档 §9 里明确列为不做。
  • --json 只输出入口模块的事件。 依赖里已经通过的声明不进事件流（一个 12 条声明的库会把入口的答题流淹没）， 依赖的问题仍以诊断形式带 file 与 module 出现。 要看某个模块自己的事件，把它当入口跑一遍即可。
  • 只有一个模块根。因此没有多根工作区，也不存在「同名模块在两处」的歧义。 跨文件互递归表达不了：import 成环是硬错， 回答是 import 成环：A → B → A，附一条「把公共部分抽到更底层模块」的提示。
  • 跨模块重名也是硬错（import-name-collision），不是遮蔽： 消息会同时给出两个来源。这是刻意的——静默首命中是最坏的一种失败。
  • --no-project 有两个入口没接。 sokonanoda grade <file> 与 sokonanoda query project 都会忽略这个旗标（grade 的调用点把 no_project 写死成 false）。要它生效，用 sokonanoda --no-project <file>。

单文件仍是默认的教学表面：画布 playground.sokonanoda 没有一行 import，判卷命令是 scripts/soko grade playground.sokonanoda。 只有当「教材库复用」或期末项目真的出现时，才升格成项目——而判卷命令不变。
