和 code agent 共用一张证明草稿纸

你和 agent 打开同一个 .sokonanoda 文件：它逐段讲课、出题，你在 sorry 处作答，判定由完整内核给出。没有文本比对，也没有正则匹配。

我想学证明 OR 我想看它是怎么造的

§1 核心循环：出题、作答、判卷、下一步

产品只有一个循环，四步。

  1. agent 在同一个 .sokonanoda 文件里逐段定义概念、写示例、抛练习，答案留成 sorry。
  2. 你在 sorry 的位置作答。
  3. 编译器把文件交给完整内核，逐条声明判定，吐出 --json 事件流。
  4. 同一份反馈也交给 agent，它据此决定下一步讲什么。

sorry 不是错误，是合法的「还没做」——内核为它发 exercise.open，不是诊断。

§2 四件能当场验证的事

每块右边都是真代码或真输出，跑得出来的命令写在图注里。

判定走完整内核，不做文本比对

前端只把源码 elaborate 成内核声明，对错由内核终审。grep 式的文本比对会假绿也会假红，所以它在硬规则里被点名禁止。

编辑器里随时能问「现在要证什么」

在 VS Code 里按 alt+b 编译，光标停在任意一行都能看到那一刻的假设与目标。面板里每个 token 都是内核给的 ty_runs / goal_runs，页面不许重新分词。

一个项目可以是多个文件

import Logic 加一个可选的 sokonanoda.toml，编译器就按闭包编译：入口文件自己不声明任何公理，名字全从库里来。跨文件练习与跨文件跳转走的是同一条路。

数学符号是课程自己声明的

卷 I 集合论里的 ∈、⊆、∪、∅ 不是内建符号，是课程用 infix / notation 写出来的源级糖。点名写法永久可用，两种写法判卷结果一致。

courses/set-theory/units/notation-cheatsheet.sokonanoda:86-89 
infix:50 " ∈ " => Set.mem
infix:50 " ⊆ " => Set.subset
infixl:65 " ∪ " => Set.union
notation "∅" => Set.empty

「充分测试是大规模合作与多次大规模重构的重要资产」——用户原话，REQUIREMENTS.md:133。

§4 它现在还不能做什么

限制

  • 没有 WASM 构建，也没有浏览器内判题。内核是 Rust，要判卷就得有本地二进制或 VSIX。
  • 没有隐式参数自动插入，也没有类型类。应用是逐位显式的，Eq.symm 这类要自己写全。
  • 这一页的演示都是预计算好的真实输出，不是在线 playground——没有一处是浏览器里现算的。
  • 卷 I 的计数口径是上一轮门禁运行（counts_source: previous-run），不是本次现场重跑。

这四条是仓库里登记在案的边界，不是「以后再说」。完整清单在 进展一页。

§5 从哪开始

  • 怎么学：教学循环、老师 agent、卡住时的三步。
  • 看它怎么判：一次判卷的完整真相，含真事件流与真拒绝。
  • 装上它：三条安装路径与排错清单。
  • 看它走到哪：真实时间线、路线图、诚实的未完成清单。
