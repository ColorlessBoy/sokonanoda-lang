内核判卷

判卷不是拿你的答案去比对一份标准答案。声明被接受，是因为完整的证明项真的过了内核。 这一页把那次检查的痕迹全部摊开：目标状态、逐字的事件流、一条端到端的拒绝， 以及诊断码从哪来。

§1 判卷的模型：一个目标状态

内核不认识「答案」这个词。它认识的是目标状态：一串假设，加一个待证的命题。 判卷就是把这两样东西交给内核，让它自己算这个命题有没有证明项。

下面这个状态不是排版排出来的，是内核回答的。左列是它给的假设，横线下面是它给的目标。

  • a : Prop

⊢

a -> a

这条状态来自本页 §2 那份源码的第 8 行。它的字段是逐字抄下来的： goal 是 a -> a，binders 是 [{name:"a", ty:"Prop"}]，status 是 open。 复现命令是 scripts/soko query state --file <上面那份源码> --line 8 --col 3。

注意两件事。第一，内核把箭头印成 ->，不是 →—— 页面照抄内核的字符，不替它美化。第二，a 在假设里和在目标里是同一个变量， 这是内核说的，不是页面猜的。

§3 一次真实的拒绝，从头到尾

第 12 行是这次判卷里唯一被拒的声明。它想证 True，却写成了 True.intro True.intro：True.intro 本身已经是 True 的证明，不是一个等着吃参数的函数，所以把它当函数用就错了。 下面是内核对这个错误的完整答复。

这条诊断只说了一件事：内核在那个位置要一个函数，拿到的却是 True.[]。 它没有说你「写错了」，它说的是它在比对什么。当拒绝的原因是两个类型对不上时， 内核会把两侧都印出来。

§4 事件词表

--json 一共发八种事件，一条一行 JSON。它们的 payload 字段只增不改， 所以消费者可以按 type 分支，而不是去猜文案。下表逐条说明每种事件 意味着什么、拿到它该做什么。

八种 --json 事件：payload 与消费方式。第三列回答「内核什么时候发它」， 第四列回答「消费者拿到它该做什么」。措辞与字段名逐条对齐 docs/protocol.md 的 §Machine events。
type payload 内核什么时候发它 消费者该做什么
decl.checked name 声明的证明项通过了完整内核 记一条判定通过。判卷的正面判据就是它，不是「没报错」。
example.checked 无 填好值的 example 通过了内核 与 decl.checked 同义，只是匿名。计数时别把它漏掉。
exercise.open name（可选） 值位是 sorry，且签名 elaborate 成功、过了内核的类型测试 当成合法的进行态，不是错误。但要清楚它的边界（下面那条注意）。
diagnostic stage、code、message、span（+ hint） 任何错误：解析、elaborate、内核或 import 阶段 按 code 分支处理，不要按 message 文案分支——文案会改，码不会。
warning code、message、hint、span 非致命的 lint；永不影响退出码 记录下来提醒学习者，但不要当失败。它不改判定，也不改计数。
expr.typed text（源切片）、inferred_type、span #check 命令 显示推断出的类型。它是一次查询的答案，不是判定。
expr.reduced text、value、span #reduce 命令 显示内核范式。同上：输出，不是判定。
decl.printed name、text #print 命令 显示声明的文本。同上：输出，不是判定。

注意

exercise.open 是合法的进行态，所以 open 计数高不代表文件有问题。 但它有一个真实的盲区：open 的计数看不出签名有没有腐烂。 签名 elaborate 不了、不是一个类型，或者 theorem 的签名不是 Prop，内核会报一条 diagnostic、把声明标成失败， 并且不发 exercise.open。

实测：printf 'theorem rotten : Nat := sorry\n' | scripts/soko - --json 回答 "code":"kernel-theorem-not-prop"、"stage":"kernel"、 "message":"rejected: theorem type must be Prop (sort 0): Nat"， 整份输出里一条 exercise.open 都没有。 所以判据是 decl.checked 与 diagnostic 这两条， exercise.open 的计数只能当参考。

§5 诊断码体系：四个阶段

每条 diagnostic 都带一个 stage 和一个稳定的 code。 stage 说明流水线的哪一段拦下了这份输入——段与段之间是真正的先后关系： 解析不过就不会 elaborate，elaborate 不过就不会碰内核。 code 说明具体是哪一种错，它的粒度细到可以让编辑器或 agent 按种类反应，而不是去匹配文案。

四个阶段与它们各自的错误码数。数字是逐条数出来的，数它的命令写在最后一列； 完整码表（每个码的含义、真实 hint、可复现片段）见诊断字典，这一页不复写。
stage 这一段管什么 码数 数它的命令
parse 词法与语法：命令拼写、括号配对、记法命令形状、namespace 开合 12 grep -c '=> "' crates/front/src/diagnostic.rs
elab 把语法树变成内核声明：名字能不能找到、binder 有没有类型、match 与 tactic 走不走得通 29 grep -c '=> "elab-' crates/front/src/compile/error.rs
kernel 真正判定证明项的那一步：类型对不对、宇宙够不够、归纳类型正不正 12 grep -c '=> "kernel-' crates/front/src/compile/error.rs
import 多文件解析：模块找不找得到、有没有成环、两个模块有没有撞名 7 grep -cE '=> "(import-|manifest-)' crates/front/src/compile/error.rs
warning 不是错误：不影响退出码，也不改判定，只是提醒 4 grep -c '=> "' crates/front/src/compile/warning.rs

合起来是 60 个错误码 + 4 个警告码（12 + 29 + 12 + 7 = 60）。 这五个数字数的是码字符串字面量的条数，不是函数个数，也不是「被构造过的次数」—— 有的码在当前版本里从来没有被构造过。完整字典，含每个码的真实 hint 与能照着跑的复现片段，在 诊断字典。

注意

docs/protocol.md 写的是人读视图印 error[<stage>]，方括号里是阶段。 本机实测不完全是：解析错误印阶段， printf 'def x : =\n' | scripts/soko - 回答 <stdin>:1:9: error[parse]: expected expected `=>`, found =； 但 elaborate 与内核错误印的是错误码， printf 'theorem bad2 : And True True := And.intro Tru\n' | scripts/soko - 回答 1:43: error[elab-unknown-identifier]: unknown identifier `Tru`。 要机器可读就用 --json 的 code 字段，别解析方括号。

教学 hint 也一样只在 --json 里：上面两条人读输出都没有 hint， 而对应的 JSON 事件带一个 hint 字段。这正是协议里那句 「the stable code and the teaching hint are JSON-only」。

§6 为什么禁止文本比对

产品的硬规则是：判定永远走内核，禁止拿文本比对冒充判定。 这不是洁癖，它防的是一个具体的失败——一门教学语言如果因为答案「看起来像」 标准答案就放行，学习者学到的就不是证明，而是猜字符串。

下面这个目标状态里，h 是 a 的证明，而要证的是 b。两个都是命题，但手上只有 a 的证明，目标却是 b——它们不是同一个命题。

  • a : Prop
  • b : Prop
  • h : a

⊢

b

这就是文本比对必然出错的地方：两段证明文本完全一样，判定却相反。 按文本打分的判卷器在这里没有第三条路——要么把 bad1 也放行 （学习者以为证完了，其实没有），要么把 ok1 一起拒掉。 两种答案都是错的，而内核两个都判对了。

内核的做法不是「再写一套规则去猜」，而是把候选术语和已写的 binders 合成一条完整声明， 交给标准流水线，由完整内核当裁判。这条设计写在 crates/front/src/judge.rs 的模块头里，第 22 行的原话是 「判定永远走 kernel，不做文本比对（REQUIREMENTS §2.8）」。 连 tactic 的下一步建议也走同一条路：内核拒绝时给出的「期望 / 实际」直接来自内核， 所以一条无效的建议根本不会被提出来。

代价是真实的：每一次判定都要合成一条声明、跑一遍完整流水线，而不是比较两个字符串。 换来的是这个页面存在的理由——上面那条 elab-tactic-failed 不是页面的判断，也不是正则匹配的结果，是内核说的。

§7 诚实的限制

上面每一条主张都附了可复现的命令。下面这四条不一样：它们是这门语言 故意不做的事，所以这一页给不出「它做到了」的证据，只能给出它做不到时的真实输出。

限制

  • 内核是一个冻结快照。 crates/kernel/**（15,174 行 Rust，数它的命令是 find crates/kernel -name '*.rs' | xargs wc -l）逐字节照搬上游， 不许改语义、不许动热路径。它内部仍用 panic 报拒绝，所以「内核说不」只能在边界上 被 catch_unwind 接成结果（crates/front/src/compile/check/mod.rs:702、 :776）。更细的内核错误分类因此一直是后续任务，而不是这一版能顺手修的东西。
  • 没有累积性。 Prop ⊆ Type 在本语言不成立（官方 Lean 4 有）。 实测：printf 'def c1 : Type := True\n' | scripts/soko - --json 回答 "code":"kernel-prop-not-cumulative"、 "message":"类型不匹配：期望 `Sort(1)`，实际是 `Sort(0)`"。 同一段代码在官方 Lean 4 里能过——这是两个语言真实的行为差异，不是 bug。
  • by 的判定不带宇宙参数。 tactic 判定时合成的那条声明，宇宙参数表是空的，所以只要目标里出现宇宙变量， 判定就会失败。实测： printf 'theorem u1 {u} (alpha : Sort u) : True := by\n exact True.intro\n' | scripts/soko - --json 回答 "code":"elab-tactic-failed"、 "message":"`exact` 判定失败：universe variable `u` is not declared in this declaration"。 受影响的只有 tactic 判定这一条路。
  • 没有源码级 print-back——但只影响一部分位置。 这一条原先在本页被写成了「目标面板一律显示点名形式」，那是过强的。 实测（钉在扩展自带的发布二进制上）表明渲染取决于光标在哪：
    • 值不是 by 块（裸 sorry 或项值）→ 走源码级渲染，记法保留；
    • by 块、第一条 tactic 之前（step -1）→ 走冻结内核的打印器，还原成点名形式；
    • by 块、走过至少一条 tactic（step ≥ 0）→ 源码级渲染，记法保留；
    • #check 一类（expr.typed）→ 内核打印器，点名形式。
    同一份文件里的三个位置实测：--line 4 --col 3（裸 sorry）答 h : x ∈ y；--line 6 --col 3（by 块第一条 tactic 之前）答 forall (x y : Nat), Mem Nat x y -> True；--line 9 --col 3 （走过一条 tactic）又答 h : x ∈ y。真实课程文件同理： query state --line 236 --col 3 答 ((∅) ∪ A) ⊆ A。
    所以限制是真的，但它是位置性的，不是全局的。要让记法在所有位置都原样回来， 得改内核的打印器或维护两套真相，两样都明确不做。

还有一条不属于「不做」，属于「说清楚」：本页引用的那份源码快照 （site/data/events.json）自己记着 source_commit 084da05 与 generated_at 2026-09-19T19:12:08+08:00，所以你可以判断它是不是已经过期， 而不是只能相信它。
