§1 先确定你问的是哪个二进制

这一页里大多数答案都取决于一件事：你的命令实际跑的是哪个 sokonanoda。 同一个检出、同一时刻，两条诊断命令可以给出相反结论——因为它们解析的不是同一个二进制。

启动器 scripts/soko 的解析顺序是四步：$SOKONANODA_BIN → 版本匹配的仓库构建 → 缓存 → 按版本钉锁定下载。文档里承诺的第五步「VS Code 扩展自带」 在代码里从未被调用（extensionServer() 只有声明、没有调用点）， 所以已经装了扩展的机器上，启动器照样会去下载。

要复核任何一条与版本有关的结论，先把二进制钉到发布产物，再确认这棵树是干净的： 

$ V=$(grep -m1 '^version' Cargo.toml | cut -d'"' -f2)
$ export SOKONANODA_BIN=~/.vscode/extensions/sokonanoda-lang.sokonanoda-$V-darwin-arm64/bin/darwin-arm64/sokonanoda
$ git status --short crates/     # 必须无输出

$ 是提示符，不用输入。平台后缀按你的机器换：darwin-arm64 / darwin-x64 / linux-x64 / win32-x64 等。

§1.1 两个 doctor，信哪一个

以 scripts/soko doctor --json 为准。它看的是整条解析链，也就是你真正会执行到的 那个二进制；sokonanoda doctor 只回答「缓存对不对」，是那条链里的一步。 下面两份输出抄自同一次真实运行，只有版本号与绝对路径用 … 省略。 

$ sokonanoda doctor --json
{"cache":"…/.local/share/sokonanoda/bin",
 "cli":{"path":"…/bin/sokonanoda","present":true,"version_match":false},
 "lsp":{"path":"…/bin/sokonanoda-lsp","present":true,"version_match":false},
 "offline":false,"ready":false,"rust_target":"aarch64-apple-darwin",
 "target":"darwin-arm64","version":"…"}
$ echo $?
3

$ 是提示符，不用输入。

$ scripts/soko doctor --json
{
  "ready": true,
  "version": "…",
  "version_source": "Cargo.toml",
  "target": "darwin-arm64",
  "rust_target": "aarch64-apple-darwin",
  "cache": "…/.local/share/sokonanoda/bin",
  "offline": false,
  "launcher": "…/scripts/soko",
  "cli": {
    "path": "…/target/debug/sokonanoda",
    "present": true,
    "ready": true,
    "marker": "…"
  },
  "lsp": {
    "path": "…/target/debug/sokonanoda-lsp",
    "present": true,
    "ready": true,
    "marker": "…"
  }
}
$ echo $?
0

$ 是提示符，不用输入。

同一个检出、同一时刻，CLI 说未就绪、退出码 3，启动器说就绪、退出码 0——因为仓库里有一个版本匹配的 target/debug 构建，启动器用了它。 两者都算对，只是回答的问题不同。

字段本身也是线索：CLI 侧是 {ready, version, target, rust_target, cache, offline, cli{path, present, version_match}, lsp{…}}； 启动器侧多 version_source 与 launcher，二进制块用 ready + marker。看到 version_match 的是 CLI 那个， 看到 marker 的是启动器那个。

§1.2 在一棵改过的树上，启动器量的是未发布的代码

启动器优先用仓库构建，所以只要 crates/ 有未提交的改动， scripts/soko 跑的就不是已发布的编译器。本机实测： scripts/soko version --json 的 cli.source 是 repo-build，而 cli.marker 还停在缓存里的上一个版本。

对读者来说这条只意味着一件事：站点上写的都是已发布版本的事实。 你要复核内核行为，就按 §1 把二进制钉到发布产物，或者确认 git status --short crates/ 没有输出。

§2 安装

这一组回答「还没跑起来」阶段的问题：拿不到包、装不上、平台没覆盖、依赖判断错。

用得了。用户与 agent 路径零工具链依赖是硬规则：Release 的 sokonanoda-cli-<triple>.tar.gz 里就是可直接执行的二进制， VSIX 平台包内嵌了 LSP 与 CLI。Rust 只有贡献者那条路需要。

Release 页有 9 个 VSIX（8 个平台包 + 1 个 universal）与 8 个 CLI tarball， 可以 headless 手动装： 

$ code --install-extension sokonanoda-darwin-arm64.vsix

$ 是提示符，不用输入。资产名是 sokonanoda-<平台>.vsix，不是 sokonanoda.vsix。

两种情况都是服务端的瞬时状态，不是你的配置。vsce publish 成功后 Marketplace 的索引还要几分钟才收录新版本，所以别查一次就判失败； Azure gallery 的 503 也是服务端故障，等恢复后重跑流水线即可。CI 每个包重试 4 次 × 30 秒。

探活只认 extensionquery：

$ curl -sS -X POST "https://marketplace.visualstudio.com/_apis/public/gallery/extensionquery" \
    -H "Accept: application/json;api-version=7.2-preview.1" -H "Content-Type: application/json" \
    -d '{"filters":[{"criteria":[{"filterType":7,"value":"sokonanoda-lang.sokonanoda"}]}],"flags":3}'

$ 是提示符，不用输入。看返回里的 lastUpdated 与 versions。按版本号拼 URL 去探测是死路，那个路由一律 404。

构建矩阵是 8 个平台，不含 linux-armhf。用 universal VSIX：它不带二进制， 按扩展自己的发布 tag 版本锁定下载兜底，从不取 latest。

这三处都按平台分支处理：二进制自动带 .exe；缓存目录回退到 %USERPROFILE%；只有非 win32 才补 0o755；python 的探测顺序是 py -3 → python3 → python。 启动器全程用 spawnSync + argv 数组，不经过 shell，所以路径里有空格也不用加引号。

x.y 是约束不是版本钉，没有对应的 release tag。启动器会明说 there is no release tag for it，并说明该文件保留 requires 作为项目契约。 两个修法：写成完整的 x.y.z，或者设 SOKONANODA_VERSION 显式给一个 tag。

§3 第一次运行

这一组里的第一条是历史上最常见的故障，其余几条大多也以 exit 3 的形式出现。

怎么知道是它。启动器拒绝 exec，并打印 expected version … (from …)、缓存 marker 与下一步命令，日志里的标记是 cache(STALE: expected X target, found M)。要看清楚，直接问版本： 

$ scripts/soko version --json

$ 是提示符，不用输入。看 cli.marker 与 version 是否一致；cli.source 告诉你它解析到了哪一环。

怎么修。把缓存刷到版本钉上：

$ scripts/soko update
$ echo $?
0

$ 是提示符，不用输入。0 = 缓存写成了；3 = 没写成，stderr 给 download: 原因。

唯一可信的证据是缓存 marker 加上缓存二进制自述的版本，不是命令打印的路径。

启动器会列出它找过的文件并给出建议，绝不猜版本。版本钉的来源链是 $SOKONANODA_VERSION → sokonanoda-version.txt → sokonanoda.toml 的 requires（完整 x.y.z 才算钉） → Cargo.toml。

规则是：出现的多个源必须一致，不一致就指名文件报错；一个源都没有也会报错。 按它点名的那个文件改，别去改别的。

chmod 与写标记失败会被容忍，但 update 会明确 exit 3 并打印 cache NOT refreshed——它不会假装成功。 出路是把缓存指到可写目录： 

$ SOKONANODA_CACHE_DIR=/tmp/soko-cache scripts/soko setup

$ 是提示符，不用输入。

判据是 refreshed 标志，不是它打印的路径：0 = 缓存写成了， 3 = 没写成。历史上有过「有可用回退就报成功」的写法，现在即使有回退也照报 3。

复核仍然是那两样：缓存 marker 文件的内容，加上缓存里那个二进制自述的版本。

启动器只解析二进制，不改 shell 的 PATH。所以一律用 scripts/soko … 形式（显式路径、可 commit、harness 中立）。

opencode 的启动插件会用 shell.env 把缓存目录注入 PATH； DeepSeek Harness 与其它 harness 没有这层注入，要么继续用 scripts/soko， 要么自己把缓存目录加进 PATH。

以 scripts/soko doctor --json 为准，完整的对照与两份真实输出在 §1.1。一句话概括：CLI 那个只回答「缓存对不对」，缓存停在旧版本时 它会报未就绪、退出码 3，即使环境其实可用。

§4 编辑器

这一组是 VS Code 里那条路：装了扩展、打开了文件，但面板或诊断不对。

旧本地构建或旧缓存静默覆盖，是历史上最常见的「版本没换」原因。扩展是 bundled-first：sokonanoda.serverPath、 SOKONANODA_LSP_BIN 与 workspace 里的 target/ 默认 被忽略，要显式打开 sokonanoda.serverOverride 才生效。

跑一次 sokonanoda: doctor，看它报的 source 是 bundled、override 还是 cache——那才是正在跑的服务器。

编译缓存是冷的，或者你在编辑器外改了被 import 的依赖文件。 命令面板里两条命令就是这条路的开关：

  • sokonanoda: build（alt+b） ——编译当前文件，CLI 会跟着它的 import 闭包，用来预热。
  • sokonanoda: rebuild（alt+shift+b） ——先跑 build --clean 丢掉缓存，再从头编一遍。

两条都把 build.file / build.clean / build.summary 事件写进 sokonanoda build 输出通道；文件编译不过时它会警告，不会静默。

那是 quarantine 属性。去掉它：

$ xattr -d com.apple.quarantine <扩展目录>/bin/<target>/sokonanoda-lsp

$ 是提示符，不用输入。VSIX 解压出来的文件通常不带 quarantine，所以这条多数时候用不上。

三道防线：下载 URL 一律带 v${version}，禁用 releases/latest； release 流程有 tag 与版本的一致性门禁；CI 有版本一致性契约测试。

默认的 bundled-first 之下，扩展与它内嵌的服务器出自同一次构建，本来不会错配。 真撞上多半是两个来源之一：你显式开了 serverOverride，或者走的是 universal 包的版本锁定下载缓存。

§5 code agent 与 harness

同一个 LSP，在不同 harness 里能用的东西不一样。这一组是 DeepSeek Harness 上的三条。

DSH 不能给工具调用注入 PATH。所以文档统一用 scripts/soko 这种显式路径的形式——它可 commit、harness 中立，opencode 与 DSH 都能直接跑。 已经有 sokonanoda 在 PATH 上时，两者等价。

DSH 的 LSP host 显式忽略服务端的 publishDiagnostics 通知， 所以判卷一律走 CLI，别等诊断： 

$ scripts/soko grade playground.sokonanoda --json

$ 是提示符，不用输入。问「某处还差什么」用 scripts/soko query state --file <文件> --line <行> --col <列>。

同一批查询也包成了 MCP 的七个工具。设计文档明确把「是否投递诊断」列为 不作为承诺，所以别按「以后会有」来规划。

DSH 没有命令黑名单。仓库自带 dsh/hooks/hooks.json 与 refuse-lean-toolchain.js，但 DSH 的 hooks 桥不做项目发现， 要在 profile 里插一行才生效；未启用时这条硬规则退回文档纪律。

验一行就知道 hook 在不在位（应退出码 2 并给出理由）：

$ echo '{"tool_name":"bash","tool_input":{"command":"lake build"}}' | node dsh/hooks/refuse-lean-toolchain.js; echo "EXIT=$?"

$ 是提示符，不用输入。匹配的是命令位的 lean / lake / leanc / lean4export / elan，所以 grep -rn lean docs/ 这类不会被误拦。

§6 贡献者

这一组只有在你改仓库代码、跑 scripts/soko gate 时才会遇到。 两条都是 exit 3，而两条都不是「你代码写错了」。

gate 的锚点用的是运行中二进制内嵌的编译器。它自报的版本与 仓库版本不一致时，锚点结果不可信，gate 直接 exit 3 并说明原因—— 这是「无法判定 ≠ 绿」。

两条出路，任选一条：

$ scripts/soko update
# 或者让运行中的二进制就是仓库构建：
$ cargo run -q -p sokonanoda-cli --bin sokonanoda -- --json playground.sokonanoda

$ 是提示符，不用输入。

课程门禁与缺口台账门禁需要 python3，探不到就 exit 3—— 绝不静默跳过。按提示装：brew install python3 / apt install python3 / winget install Python.Python.3。 Windows 上还认 py -3。

请注意

改教学 crates 时不要跑 cargo fmt --all：它会重排冻结的内核快照。 用 cargo fmt -p sokonanoda-front -p sokonanoda-cli -p sokonanoda-lsp -- --check， 或者干脆交给 scripts/soko gate。

另外，扩展改动的三层验证里那条真 VS Code 的 E2E 常卡在下载上—— 那属于网络问题，见 §7 的最后一条。

§7 离线与网络

这一组的共同点是：命令本身没错，是它要的那份数据拿不到。

下载需要网络，这一条没有绕法。设了 SOKONANODA_OFFLINE=1 时启动器会给一句 人话并 exit 3，而不是卡在超时上；已经缓存了匹配版本的机器 照常可用。

真正的离线路径是 VS Code 扩展：有平台包的机器装完扩展就全程不需要网络， 语言服务器与 CLI 都在包里。

Node 的 fetch 不读 HTTPS_PROXY。 启动器因此优先用 curl（curl 认代理与企业 CA）， 失败才回落到 fetch；失败时把 curl exit … / fetch failed … 写进 stderr，所以你能看出是哪一条路断的。 

$ HTTPS_PROXY=http://127.0.0.1:7890 scripts/soko setup

$ 是提示符，不用输入。代理地址换成你自己的。

@vscode/test-electron 也不读 HTTPS_PROXY， 它只认 npm 的代理变量。所以要单独给这两个变量： 

$ npm_config_https_proxy=http://127.0.0.1:7890 scripts/vscode-e2e.sh --version 1.106.0

$ 是提示符，不用输入。1.106.0 是扩展声明的最低 VS Code 版本，也可以换成别的。

另外它的下载超时是「无数据 15 秒即中断」，与总时长无关——拉老版本时可能反复断在同一个点， 重试通常能过。

  • 能修好的：环境、缓存、代理、PATH、平台
  • 修不好的：内核没有的能力、没发布的构建、没覆盖的平台

§8 明确不做的事，与已知的粗糙边缘

排错页最容易暗示「什么都能修好」。下面这些不是配置问题，改环境也修不好， 写在这里免得你照别处的说法去试。

限制
  • 没有 WASM / 浏览器构建。浏览器里跑不了内核，所以本站的功能展示 全部来自预计算的真实输出——这里不是一个能点的在线判题器。
  • 启动器没有「VS Code 扩展自带」这条回退。解析链只有四步： $SOKONANODA_BIN → 版本匹配的仓库构建 → 缓存 → 按版本钉锁定下载。 AGENTS.md 与 skills/README.md 里写的第五步是死代码， 不要按它规划。
  • 不为使用仓库安装 Rust / cargo。Rust 只属于贡献者路径； 用户与 agent 一律走 Release 二进制或平台插件。
  • 不用 releases/latest。下载一律按仓库版本锁定， 禁用「取最新」这条捷径。
  • 不调用官方 Lean 工具链。lean / lake / lean4export / leanc / elan 都不碰； opencode 由 opencode.json 的权限规则强制，DSH 靠 hook 或文档纪律。
  • 扩展内不做二进制自动更新。换版本要重装扩展， 扩展与它内嵌的服务器永远同版本。
  • 平台矩阵是 8 个（macOS arm64/x64、Linux x64/arm64、 Alpine x64/arm64、Windows x64/arm64），不含 linux-armhf； 没被覆盖的平台走 universal 包的版本锁定下载。
  • DSH 侧不做 MCP prompt 模板、不做服务端推送——DSH 不支持。
已知的粗糙边缘
  • 缓存过期即拒绝运行是设计如此，不是 bug。但它会以「工具坏了」的样子 出现，所以先跑 scripts/soko version --json 看 marker。
  • 两个 doctor 的判定面不同，结论可以相反。 以启动器的那个为准，见 §1.1。
  • 启动器优先用仓库构建，所以在一棵有未提交改动的树上，它量的是未发布代码。 见 §1.2。
  • query check 对「用了 import 来的记法」的文件会报假红。 入口先按单文件解析，拿不到继承来的记法表，那条 parse 诊断会留在 failed[] 里， 而同一个文件 grade --json 是干净的。要验证这类文件，一律用 scripts/soko grade <文件> --json，别用 query check。 自己声明的记法不受影响。
    版本标注：这是当前发布版本的行为。未发布的下一批改动里 它已不再复现（同一条命令、同一个文件，工作区构建退出 0）——发布之后请重测。 本站写的是已发布版本的事实，所以在这条被重测推翻之前，上面那句仍是你能依赖的规矩。
  • soko/nextHole 无法在同一源码位置的多子目标之间导航， 同址子目标只能整组走。
未证实

下面这几条没有机器可验证的证据，本站按「未证实」标注，不当作支持的能力。

  • cargo binstall sokonanoda-cli 与 mise github:ColorlessBoy/sokonanoda-lang。 README 提过这两条，但全仓没有任何 [package.metadata.binstall] 配置， 两者都依赖第三方工具自身的 GitHub Release 启发式。不要把它们当安装路径。
  • docs/design/deepseek-harness.md 里写的技能路径 .dsh/skills。实际落地在 .agents/skills/。
  • docs/RELEASE.md 说 release 资产共 25 个。 实测是 26 个（8 个 LSP tarball + 8 个 CLI tarball + 9 个 VSIX + 1 个 SHA256SUMS）。
  • 文档里任何「当前版本 playground 的期望计数」。 那些数字都已过时；要引用就先自己跑一遍判卷。

下载下来的每个资产都能校验：release 页有 SHA256SUMS， 还有 SLSA provenance 可以验—— gh attestation verify <文件> -R ColorlessBoy/sokonanoda-lang。
