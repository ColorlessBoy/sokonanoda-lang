产品

与 Lean 4 / Coq / Agda 对照

如果你已经会一个证明助手，这一页回答「这东西跟我有什么关系」。 先说它是什么，再并排比，再说别人强在哪——最后才说它故意不一样在哪。

§1 先说它是什么

sokonanoda 是一门课程序列的教学语言。课程只有两卷： 入门课 11 个单元，卷 I 集合论 12 个单元、36 个目标、329 条 checked。 它不是通用证明助手，路线图里也没有往那个方向走的计划。

它与 Lean 4 的关系只有一条：教学语法是真实 Lean 4 的子集。 集合的定义与 Mathlib 逐字相同，两边写的都是 def Set (α : Type) : Type := α -> Prop。 语义零差距，差的只有记法。 它不调用官方 Lean 工具链，也不是 Lean 4 的兼容实现。

  • 课程序列：入门课 11 单元 + 卷 I 12 单元
  • 一个冻结的内核当唯一裁判
  • 使用路径不要求 Rust / Lean 工具链

⊢

它不是通用证明助手

所以下面的对照不是「谁更好」，而是「各自被造成什么样」。 大多数情况下，如果你要证真实数学，答案是你应该用 Lean 4。 §3 会把这件事说透。

§2 四条路线并排

只有七行，因为只有七件事会影响你的选择。这不是功能矩阵。 功能矩阵数的是「有没有」，这张表问的是「为什么长成这样」。

§3 别人强在哪

先把话说尽：如果你要证真实数学，你要的是 Lean 4。 如果你手上已经有 Coq 代码，你要的是 Rocq。这一节列的都是真的短处。

库大两个数量级

Mathlib 的 Data/Set/ 一个目录就有 46 项；agda-stdlib 有 1,114 个模块； Coq.Sets.* 有 22 个模块；外面还有 stdpp 与 MathComp。 我们的课程标准库是 74 条声明、8 个模块——差距不是一点。 课程里要用的每一条引理都得自己写，写的时候撞到「这东西本该有」就记一条缺口。

真在做研究

Lean 侧，flypitch 的 independence_of_CH 是 Wiedijk「100 定理」第 24 条的条目； Foundation 里有 zfc_consistent；con-nf 证 Quine NF 的一致性。 Rocq 在那张页面上占 80 条。Cubical Agda 里有 ZF 的累积层模型。 本项目一条都没有，路线图里也没有。

工具链成熟

rocqchk 能脱离证明器单独重查已编译的库；Agda 有 .agdai 与 _build/<版本>/ 这样的接口文件当缓存单元； lean4game 是长驻服务，把 goal state 增量推给前端； stg4 有 51 关、8 个 world、随进度递减的提示密度与浏览器端进度存储。 我们这边不一样。项目模式没有跨模块增量，REPL 没有行编辑，也没有浏览器内构建。

§4 我们故意不一样的地方

上一节是代价，这一节是选择。五条，每条都能点开看到真实证据。

  • by 白名单：7 个 tactic
  • 一个冻结的内核，判定不做文本比对
  • 缺口台账 24 条，open 0

⊢

一个不给 simp 的环境，能逼人把每一步写出来

白名单是封闭的：七个，一个不多

by 块只认 intro、exact、apply、 assumption、rfl、match、sorry。 白名单外的写法在 parse 阶段就被拒，连 elaborate 都到不了。 这是本页第一批实测结论之一：量的是已发布的 —，不是工作树。

unexpected-tokenparse 阶段

未知 tactic：by 块只支持 intro / exact / apply / assumption / rfl / match / sorry（白名单），发现 Token { kind: Ident("simp") … }

这里的写法不符合当前课程语法。检查命令拼写、括号配对，以及是否多写了还没学过的符号。

上面这条来自 by intro a; simp，消息里的 span 字段略去。 换成 rw [a] 死得更早： [ 根本不是这个语言的 token，消息是 「expected a valid .sokonanoda token, found [」。

判定权从人手里拿走

教学主张只有一句：把判定从老师、答案册和自己的直觉手里拿走，交给一个冻结的内核。 课程内容于是只剩下「讲什么、按什么顺序讲」。 by 块不是第二套语义——进内核前它先降级成 lambda， tactic 判定走合成完整声明交完整内核裁决那条路。

代价是内核不能动：crates/kernel/** 一个字节不改， bugfix 必须带三层回归测试。换来的是判定结果可复现—— 卷 I 的 329 条 checked、99 条 open、0 条 rejected，每次都能重跑出来。

零工具链安装

启动器按固定顺序找二进制：$SOKONANODA_BIN、版本匹配的仓库构建、 缓存、最后按版本钉锁定下载。Release 的 CLI tarball 里就是可直接执行的二进制， VSIX 内嵌 LSP 与 CLI。使用路径不要求 Rust，也不要求 Lean。

 "target": "darwin-arm64", "offline": false,

 "lsp": {"present": true, "ready": true}}

$ 是提示符，不用输入。启动器本身是一个零依赖的 Node 脚本——需要 Node，不需要 Rust。

agent 与学习者读同一份反馈

同一份判定有三个视图，来自同一份真相。grade --json 是全量事件流； query check 之类是单 JSON 对象；LSP 的诊断与 goal 面板是第三个。 这样做的理由是产品的用户里本来就有 code agent—— 一份只对人友好的反馈会逼出第二套实现。

课程驱动开发

写课程时每撞到一次「这东西本该有」，就记一条缺口。 台账现在有 24 条：22 条已修、2 条有绕法、0 条开着。 课程标准库的 74 条声明里，有 32 条是这么从零补出来的标准库欠账。 这条纪律也反过来塑造了语言：先撞到缺口，才加下一个语法点。

白名单是发布事实，不是路线图

「七个」写的是已发布版本的事实。这一页的每个内核行为， 也都是在发布产物上量的，不是在工作树里量的。

为什么必须说清楚：两者现在不一致。仓库的工作树里有一批未提交的 WIP， 给 by 块加了 constructor、cases、 left、right、use、exfalso。

实测：这六个在发布版本上全部是 parse 阶段的 unexpected-token， 在工作树的构建上则能通过。所以这一页的「七个」随时可能过期， 而它过期的方式恰恰是变多。任何时刻要核对，请钉住发布产物再跑： 把 SOKONANODA_BIN 指向 VS Code 扩展自带的那个二进制。

§5 从别处来

这一节只讲一件事：哪些肌肉记忆能带过来，哪些会撞墙。 每条「不成立」都跑过，消息逐字来自发布版本的 --json 事件流。

从 Lean 4 来

会眼熟的：theorem、def、 inductive 配 ctor 与 end、 声明级 binder、箭头与 forall、by 块、 match、rfl。目标状态也是 Lean 的形状： 假设在上，⊢ 与目标在下。 最能直接搬过来的是集合本身：def Set (α : Type) : Type := α -> Prop， 与 Mathlib 的定义逐字相同。

会撞墙的第一件事是 tactic。simp、rw、 constructor、cases、use、omega 都没有。白名单只有七个，白名单外的写法在 parse 阶段就被拒； §4 那条诊断就是 by intro a; simp 的真实输出。

第二件是隐式参数。这里没有隐式实参插入，隐式 binder 只是打印样式， 签名要显式给全参数。裸写 Eq 默认宇宙层级 0，数值等式必须写 Eq.{1}。实测 theorem t : Eq Nat 0 0 := by rfl 给出 elab-tactic-failed，消息是 「rfl 判定失败：两边不相等（期望 Sort(0)，实际 Sort(1)）」； 改成 Eq.{1} Nat (1 + 1) 2 就过。

第三件是累积性。Prop ⊆ Type 在这里不成立， 官方 Lean 4 成立。实测 def T : Type := True 被内核拒， 码是 kernel-prop-not-cumulative，消息是 「类型不匹配：期望 Sort(1)，实际是 Sort(0)」。 它的 hint 逐字承认「官方 Lean 4 有累积性，同一段代码在 Lean 里能过」。

还要留意的三处：没有 typeclass、structure、instance、 section、variable 与 macro； match 没有 as 与 or 模式、没有多 scrutinee、 没有 if/then/else 表达式； intro 一次只收一个 binder，intro a b h 是 parse 错误， 要拆成三次。

最后一处比较微妙：目标面板的渲染取决于光标在哪。 在课程文件里实测 query state --file courses/set-theory/units/notation-cheatsheet.sokonanoda --line 236 --col 3， 目标是 ((∅) ∪ A) ⊆ A，记法保留了。 但 by 块的第一条 tactic 之前、以及 #check， 走的是冻结内核的打印器，给的是 Set.mem α a A 这样的点名形式。 这不是 bug，是「内核不知道记法」的直接后果。

从 Coq / Rocq 来

会眼熟的：内核当唯一裁判这件事本身——rocqchk 能脱离证明器单独重查已编译的库，与本项目的形状一致。 集合就是谓词也一样。Coq 的 Ensemble := U -> Prop 与这里的 Set α := α -> Prop 是同一个构造； 连「靠一条外延性公理把等式撑起来」都想到了一起。

会撞墙的是 tactic 语言。rewrite、simpl、 auto、lia、ring 都不存在。 这里的 apply 只做一件事：若 f : A1 -> … -> An -> B 而目标正是 B，就把目标换成那几个前提。 intro 一次一个 binder，没有 intros x y z。

工程形态也不同。这里没有 _CoqProject、 -Q 与 From … Require 那套逻辑路径； 用的是 import 配 sokonanoda.toml，模块根由清单推出来。 没有 .vo 那样按模块缓存的接口产物，项目模式也没有跨模块增量。 typeclass、Instance 与 Hint 数据库同样没有。

库的量级要对齐预期。Coq.Sets.* 有 22 个模块， 里面有 Powerset、Finite_sets、Image、 Relations_1 到 Relations_3。名字能对上一些， 覆盖面对不上——这边是 8 个模块、74 条声明。

从 Agda 来

洞是一等公民这点两边都认同，用法不同。Agda 的 ? 与 {! !} 由编辑器交互式 refine。这里的洞只能写在声明的值位， 写在别处报 elab-hole-misplaced；期望类型由内核给出， 没有交互式 refine。

另有一处容易串。Agda 官方把类型宇宙命名为 Set； 这里的 Set 是集合论意义的集合（α -> Prop）。 同名不同物，读代码时留意。

§6 该选哪个

要证真实数学、要用 Mathlib，用 Lean 4。手上已经有 Coq 代码、 或者在做编程语言与验证，用 Rocq。要依赖类型编程、要洞驱动开发，用 Agda。 要在两门课里从零学集合论、又不想装工具链，用这个。

如果你已经会其中一个，这个语言的边际价值只有一条。 它是一个不给你 simp 的环境： 每一步都得自己写出来，写不出来就是写不出来，内核不会替你补。 这是它唯一的教学主张，也是它全部的野心。

  • 你已经会 Lean 4、Coq/Rocq 或 Agda
  • 你要在两门课里从零学集合论
