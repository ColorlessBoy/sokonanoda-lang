过程与信任

工程与证据

这个项目的过程就是它的质量机制。这一页不写「我们很严谨」，只写清三件事： 每条规则被哪道门禁强制执行、每个数字用哪条命令量出来、以及门禁挡不住什么。

§1 主张：过程就是质量机制

「判定永远走真内核」这句话本身没法验证，除非你能看见内核真的拒过东西。 所以这个项目把能自动判定的东西全部写成门禁，把不能自动判定的东西写进台账， 再给每条台账记录配一条能重跑的命令。这一页上的每个数字都来自仓库里的文件， 出处写在数字旁边。

这套做法有一个直接后果：项目的历史是可查的。CI 红过 35 次，每一次的原因、 修复和预防都留在 docs/CI-FAILURES.md 里，其中 10 次是同一个外部服务 超时——这条记录比任何「稳定可靠」的形容词都更能说明维护状态。

  • 门禁 : 6 步，一条命令
  • 台账 : 4 本，每条带复现或命令

能被重跑的规则 = 规则

这一页的数字都能自己量一遍

每个数字旁边都有产生它的确切命令。仓库公开，命令可以直接复制粘贴。 量不出同样结果的，这一页会写明原因，而不是把数字删掉了事—— §5 就有一条这样的记录。

§2 六道门禁：每次 push 跑什么

贡献者侧一条命令 scripts/soko gate 跑完六步；CI 侧把同样的判据拆进 .github/workflows/ci.yml 的 job。先给对照，再给「挡不住什么」。

后两步依赖 python3。探不到解释器时门禁不会静默跳过： 它以 exit 3 退出并说明原因——「这一步没跑」和「这一步跑过了」必须是两个 不同的结果。

本地门禁与 CI 不是同一件事

这是这一页最该说清楚的一段。画布锚点在 scripts/soko gate 里， 但它没有对应的 CI 步骤：CI 的 test job 跑的是全量测试、协议一致性、 课程门禁与台账门禁，锚点那一步由 CLI 的 gate 子命令在本地执行。 在整个仓库里，playground.sokonanoda 只有这一处会去编译它， 其余的命中都是测试里的注释与技能文件的路径断言。

所以「本地绿」与「CI 绿」覆盖的不是同一组判据：锚点绿只说明你手上这个二进制 还能编过那份画布。反过来说，CI 绿也不保证锚点绿。 

$ scripts/soko gate
+ cargo fmt -p sokonanoda-front -p sokonanoda-cli -p sokonanoda-lsp -- --check
+ cargo clippy --workspace --all-targets
+ cargo test --workspace --locked
sokonanoda: gate PASS

$ python3 scripts/gap.py selftest
gap.py selftest: 14 条判据 + clean_env 剔除覆盖 全部成立。

$ 是提示符，不用输入。前四行是 gate 自己打印的步骤头与结论；最后两行单独跑台账自检的输出。锚点没有独立的命令行——它在 gate 内部执行。

锚点还带一个版本前提

锚点用的是运行中二进制内嵌的编译器。如果它和仓库版本不一致 （旧缓存、旧构建），gate 直接 exit 3，不拿旧逻辑判新代码。 这个前提只在「当前目录有 Cargo.toml」时才检查—— 在子目录里跑，它读不到仓库版本，这道保护就退化成无操作。

第三类的处置值得单独看一眼，因为它有一次没有按最省事的方式做： 哨兵红的时候，直接调宽阈值就能变绿。前三轮修的是采样口径（进程内串行 + best-of-N）， 阈值一个都没动；第四轮同一个用例在两次 CI 上一绿一红，于是把四次 CI 日志里的实测值 捞出来量分布，发现同一份代码跨 runner 实例有 4 倍方差、阈值正好落在噪声带里—— 这时候才改阈值，并把那组实测数字写进用例注释。 改与不改，依据都是量出来的分布，不是感觉。

性能台账是哨兵，不是基准

这 14 条记的是本机、同一套采样口径下的毫秒数，用来发现「这次改动让某条路径变慢」， 不是用来和别的项目比。每条都带版本与 commit，所以两次记录之间可比； 跨口径不可比。外部基准仍是 opt-in，项目对外没有发布过性能对比结论。

§4 缺口台账：写课程写出来的语言缺口

这四本里最值得看的是缺口台账，因为它是被写课程逼出来的。 写卷 I 集合论的时候，每撞到一个语言写不出来的地方，就记一条：最小复现是什么、 官方 Lean 4 里这段是什么行为、现在怎么绕、绕的代价是什么、卡住了哪些单元。

结果是 24 条，分布在 4 个种类与 3 个级别上。22 条已关账，2 条是长期绕行 （workaround，写明了代价），open 为 0—— 这个 0 不是「没有问题了」，而是「记下的每一条都有了结论」。

复现分两种：.sokonanoda 画布走判卷，自断言 .sh 脚本走退出码。 脚本的退出码有三档约定，含义写进台账协议里：

退出码含义接下来做什么
0缺口仍在，且与台账 today 字段描述一致正常状态，不用动
1行为变了（很可能已修复）回来更新台账，写 fixed_in，并升级课程

期望值默认从 status 推导：fixed 的复现应当转绿， open 的应当仍然复现。但有些缺口的「修好」恰恰是判红—— G-01 钉的契约是「签名写错必须被拒」，所以它必须在台账里写显式的 repro_expect: rejected 覆盖推导。这个字段只吃四个值 （clean / rejected / exit0 / nonzero）， 取值与复现类型不匹配、或拼错，check 直接判不一致并把原因印出来。

§6 发布：人只做两件事

版本号写死在两处：Cargo.toml 的 workspace 版本与 editor/vscode/package.json。这两处必须一致——有一条契约测试守着 （cargo_and_extension_versions_match），auto-tag job 自己 也会再比一次，不一致就不打 tag。发布流程是：改这两处、推 main， 之后 auto-tag 打 tag 并触发 release workflow。

三个 workflow 各管一段：ci.yml（lint / auto-tag / test / e2e）、 release.yml（build / package-vsix / github-release / marketplace-publish）、pages.yml（本站部署）。 auto-tag 依赖 lint、test 与两条 e2e 腿；课程门禁与台账门禁就挂在 test job 里，不新建 job——所以课程判红会直接挡住打 tag，不会先发一个坏版本再补救。

发布产物与校验方式的细节在版本历史那一页； 这一页只记与「过程」有关的一条：每个 Release 附 SHA256SUMS， 并由 CI 的 Attest build provenance 步骤签发构建来源证明， 所以「这个二进制是从这个 commit 构建的」是可校验的，不需要信任发布者。

§7 这套过程还没覆盖的地方

上面每一节都在讲「有什么」，这一节讲「缺什么」。下面每一条都是实测或实测不到的， 不是免责声明。

工程债：几个文件比登记时更大

仓库的惯例是「文件接近 500 行即考虑拆分」。下面这 8 个文件远超这条线， 括号里是本次实测的行数：

  • crates/front/src/compile/tests.rs（7926）
  • crates/front/src/parser.rs（4941）
  • crates/front/src/compile/elab.rs（4184）
  • editor/vscode/extension.js（1880）
  • crates/lsp/src/lib.rs（1610）
  • crates/front/src/compile/check/walk.rs（1311）
  • crates/front/src/compile/check/mod.rs（856）
  • crates/front/src/compile/check/kernel_phase.rs（527）

这 8 个数比 docs/HANDOVER.md 里登记的旧值更大—— parser.rs 从 2065 涨到 4941，elab.rs 从 2854 涨到 4184。 2026-09-18 拆掉了一个约 1174 行的单函数（验收手段是二进制对拍：改动前后跑同一批 画布，标准输出逐字节相同），但语言在长，几个大文件比登记时更大。 这是公开可查的欠账。

过程本身的三处缺口
  • 画布锚点不在 CI 里（§2）。本地门禁与 CI 覆盖的判据不同， 这是两者之间最实质的一处差异。
  • CI 失败台账没有自动门禁。「同一类失败不犯第二次」是一条纪律， 靠人在每次红的时候写一条。35 条记录说明这条纪律被执行了， 但它不像缺口台账那样有脚本兜底。
  • 冻结内核不在格式门禁的范围内。cargo fmt 只点名教学三个 crate，这是刻意的（--all 会重排内核快照），代价是内核的格式 没有机器守护。
未证实，所以这一页不写

三件事没有可复现的来源，因此全站不出现：

  • 性能倍数。「相对官方内核 10–100 倍」写在需求文件里，是项目的定位表述， 不是本仓库量出来的结果；外部基准仍是 opt-in。这一页只给本机同口径的哨兵数字， 不给跨项目对比。
  • 用户数 / 下载量 / 教学效果。仓库里一条来源都没有。
  • 历史课程计数。文档里散落的旧快照（如「355 checked」「308/93」） 是当时的实测值，课程在长，它们今天已经不对。要引用课程计数， 一律以课程门禁当次输出为准。
