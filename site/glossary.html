术语表

这一页只做一件事：把全站到处在用、却从没定义过的词逐个定义清楚。 每条一句话，外加一个「去哪一页看它真的被用」。

§1 先看一条横线：四个词一次定义完

下面这张图里的每一个字都来自内核，不是画出来的：它是 query state 在一个真实练习上返回的目标状态， 源码是 theorem and_intro_demo (a b : Prop) (ha : a) (hb : b) : And a b := sorry。

  • a : Prop
  • b : Prop
  • ha : a
  • hb : b

⊢

And a b

横线上面的四行叫假设（hypothesis）：此刻手里已经有的东西， 每行形如 名字 : 类型。横线下面的叫目标（goal）： 此刻要交出来的东西。两半合起来叫目标状态（goal state）。 那条横线本身叫 turnstile（⊢，读作「由此可推出」）。

一个术语表如果只给定义、不给「它在哪被用」，就还是一张死名单。 下面四张表按语言 / 内核 / 工具 / 课程分组， 第三列永远是链接——点开就是那个词真正在起作用的地方。

§2 语言：源文件里看得见的东西

这一组是写 .sokonanoda 文件时真正会打出来的词。 它们的共同点是全部看得见——你能在文件里指出它占哪几行。

语言层的术语。第三列是这个词被展开讲的那一节，点开就是它的真实例子。
术语 一句话定义 在哪一页展开
声明 declaration 源文件里的一条顶层命令：def / abbrev / theorem / example / axiom，或者整个 inductive … end 块。 判卷的每一个计数都以它为单位。 语言 §2 声明：五种拼写
项 term 有类型的东西。本语言里「证明一个命题」就是「交出一个该命题类型的项」， 没有第二套含义。 策略 §3 证明就是项
by 块 值位写 by、后面跟一串 tactic 的写法；它在进内核之前被降级成 lambda， 所以不是第二套语义。 策略 §1 by 块不是第二套语义
tactic by 块里的一个动作关键字，白名单只有七个：intro / exact / apply / assumption / rfl / match / sorry。 策略 §2 七个 tactic，一个不多
match 按构造子分情况的写法，值位与 tactic 位都能用；它降低为归纳类型的消去子 （<类型>.rec）的一次显式应用。 语言 §4 值位的三种关键字
归纳类型 inductive type 用 inductive … ctor … end 一整块声明的类型；Nat、Bool、 Or 与课程里的 Color、Vec 都是。 语言 §3 归纳类型：一个块，四种行
构造子 constructor 归纳块里 ctor 那一行，是造出该类型元素的方式。规范名带类型前缀 （Or.inl），裸名只是解析别名。 语言 §3 归纳类型
消去子 recursor 归纳块里 rec 那一行——可以省略，前端会按内核期望的形状自动派生。 它规定怎么按构造子逐情况计算，iota 行给出它在每个构造子上的计算规则。 语言 §3 归纳类型
记法 notation 用 infix:50 " ∈ " => Set.mem 这类命令声明的源级糖： 只把源文本重写成既有的应用形状，不产生事件、不进声明表、也不进目标视图。 语言 §5 名字、作用域与记法
作用域命令 namespace 给块内的声明名加前缀；open 只影响名字解析、 不重命名任何东西；export 与 open 同形，但会跟着 import 传到下游。 语言 §5.1 namespace / open
import 写在文件最上方、任何声明之前的模块引用；一旦出现，编译单位就从「单文件」 升级成「入口 + import 闭包」。 语言 §6 多文件
模块 module 一个 .sokonanoda 文件在项目里的名字 = 相对模块根的路径去掉扩展名、 目录换成点（Foo/Bar.sokonanoda 就是 Foo.Bar）。 项目 §1 模块名就是路径
清单 manifest 模块根目录里的 sokonanoda.toml，只认 name / requires / src 三个可选键；它最重要的作用是告诉工具 「模块根在哪」。 项目 §1.1 根从哪来

§3 内核：判定怎么发生

这一组是判卷时才会出现的词。它们的共同点是：你在源文件里指不出它—— 它描述的是「一份文件被读进去之后发生了什么」。

内核与判定的术语。第三列指向这个词真正起作用的那一节。
术语 一句话定义 在哪一页展开
elaboration 精化 把表面语法翻译成内核项的那一步：解析名字、解析宇宙参数、折叠 binder。 这一步出错就直接返回，根本不碰内核。 内核 §2 从 12 行源码到事件流
kernel 内核 可信的类型检查器（crates/kernel），也是全站唯一的裁判。 它只回答「这个项的类型对不对」，不回答「你想证的是不是这个」。 内核 §2 一次真实的判卷
判定 judgement 内核给出的「成立 / 不成立」：成立发 decl.checked，不成立发 diagnostic。front::judge 是另一件事——它是 by 块的 tactic 判定器，最终仍把合成好的完整声明交给同一个内核。 内核 §6 为什么禁止文本比对
环境 environment 内核里那张「已声明的名字 → 声明」的表，外加一个可见前缀： #check 只看得到写在它之前的声明。 内核 §2 一次真实的判卷
宇宙 universe 类型的类型。Prop 是 Sort 0，Type 0 是 Sort 1，Type n 只是 Sort (n+1) 的解析糖； 把 #check Prop 交给内核，它答 Prop: Type 0。 语言 §2 声明 · 课程 §2 单元⑤
累积性 cumulativity 官方 Lean 4 里 Prop 可以当 Type 0 用；本语言 故意没有这条规则，所以 def X : Type 0 := True 被内核拒： 期望 Sort(1)，实际 Sort(0)。 语言 §8 诚实的限制
目标状态 goal state 一个位置上「手里有什么 + 要证什么」的合称，内核渲染成「假设在上、 ⊢ 目标 在下」——就是本页 §1 那张图。 内核 §1 判卷的模型
假设 hypothesis 目标状态里「手里已经有的东西」，每行形如 名字 : 类型； query state 的 JSON 里这个数组的字段名是 binders。 内核 §1 判卷的模型
洞 hole 源文件里一个还没有项的位置，sorry 占着它。它有稳定 id （声明名:序号，例如 and_intro_demo:0）和字节区间—— 所以洞是位置，不是声明。 Agent §3.3 问「这里还差什么」
sorry 合法的「还没做」占位符：文件里有它，退出码仍然是 0，声明发 exercise.open 而不是诊断。它在 by 块里是同一个意思。 策略 §2.7 sorry：合法地留空
诊断 diagnostic 前端或内核说「不」的那条结构化消息：stage（parse / import / elab / kernel）+ code + message + 教学用的 hint + span。它把退出码变成 1。 诊断字典 §1 四个阶段
警告 warning 非致命 lint，一共四个码；永不影响退出码。 所以判卷只看诊断、不看警告。 诊断字典 §5 警告与诊断不是一回事
--json 事件流 grade --json 的输出：每行一个 JSON 对象（JSON Lines）， 每个事件都带 type 与 human，一共八种 type。 Agent §3.1 每行一个事件
闭包编译 closure compilation 带 import 的文件不是单独编译的：入口加上它（直接或间接） import 的全部模块构成一个闭包，整包一起编译；闭包里任何一个模块坏了， 依赖它的模块都不编译。 项目 §3 闭包编译
