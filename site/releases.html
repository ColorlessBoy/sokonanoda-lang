版本历史

这一页是台账，不是故事：每一版装了什么、落在哪一天、还算不算被支持， 以及下载下来的东西怎么自己验一遍。故事在进展那一页。

§1 当前版本

  • — 当前版本 · 2026-09-19 发布

状态是当前——唯一还在收修复的一版。它装了三件事：

  • abbrev 与记法的几个拼写（prefix / postfix / binder_notation / scoped）进了唯一的关键字源， 于是语法高亮、语义 token、Infoview 代码围栏与补全列表同一轮跟上—— 两份词表由一条契约测试钉死，不许漂移。
  • 宇宙层级算术 u+1 可写，prelude 的 Eq.mp / Eq.mpr / cast 因此变成宇宙多态，Eq.ndrec 一并进来。调用方式也跟着变：本语言不插隐式参数、不推断宇宙， 裸写仍然落在 Type 0。
  • 课程清单 v2：课程树按 卷 → 章 → 单元 分组，单元事件带上 volume / chapter / tags。 切换是数据驱动的，旧的扁平清单走同一棵树，行为逐字节不变。

出处：editor/vscode/CHANGELOG.md 的最新条目（用户可见文案的权威来源）。 版本号由 site/data/site.json 在浏览时填进来，页面里不写死—— 写死的版本号一定会过期，全站的卫生检查会直接拒绝它。

§2 支持状态：版本号旁边那两个字

做法借自 Python 文档把 3.14 (stable) / 3.9 (EOL) 写在版本号旁边的习惯：读者不该去猜「这一版还在不在维护」。本项目只有三档， 其中一档是空的——那正是要写出来的部分。

支持状态的三档标签，以及每一档在仓库里能查到的依据。
标签 含义 依据（可复跑）
当前 只有最新的一版。修复只往这里落。 git tag --sort=v:refname | tail -1
已被取代 比当前旧的每一版。Release 资产、校验和与来源证明都还在，随时可以下载核对； 但它们不会收到修复——要修复就换到当前这一版。 gh release list --limit 100
长期支持（LTS） 本项目的标签集合里没有这一项。没有 LTS 分支，也没有 backport： 唯一的修复路径是发新的一版。 git branch -r → 远端只有 origin/main（外加 origin/HEAD 这个别名）；没有发布分支、没有 backport 分支

「已被取代」不叫「EOL」，因为这里没有单独的停止支持公告：一版被下一版取代的那一刻， 它就退出维护。这套模型是刻意的——14 天里发了 69 个 tag，维护窗口以天计； 给旧版开分支意味着同时维护多棵树的版本不变量，而那个不变量是这条发布链的承重墙（§4）。

你手上跑的是哪一版，别靠记忆：scripts/soko version --json 报的是解析出来的仓库版本与缓存标记； 页脚的「当前版本」报的是本站数据里的当前版本；VS Code 里用 sokonanoda: doctor 看扩展与它内嵌的服务器对不对得上。

§3 台账：13 天，69 个 tag，75 条版本条目

一天发很多版是常态，所以这张表按天聚合：一行就是一天， 「装了什么」一列写这一天所有版本的用户可见变化。铺开 69 行会让最密的那一天 吃掉整张表，读者反而看不出发生过什么。

日期只有一种口径

有 tag 的版本取 tag 指向提交的日期 （git log -1 --format=%ad --date=short <tag>）； 没有 tag 的版本取 editor/vscode/CHANGELOG.md 的标注日期。 全表只用这一种约定，不混。

两种来源并不总是一致：19 个版本的 CHANGELOG 日期比 tag 提交日期早一天 （多是跨零点提交）。选了 tag 日期当口径，就意味着这 19 处按 tag 的那天落行—— 比如 match 那一批的 CHANGELOG 标着前一天，表里落在后一天。

每天到底发了哪些版本、每个版本落在哪一天，页面里印不出来（原因见下）， 但仓库里两条命令就能列出来： 

$ grep -n '^## \[' editor/vscode/CHANGELOG.md | head -12
$ for t in $(git tag --sort=v:refname); do
    printf '%s  %s\n' "$t" "$(git log -1 --format=%ad --date=short "$t")"
  done | tail -12

$ 是提示符，不用输入。第一条给出版本号、CHANGELOG 日期与行号； 第二条给出每个 tag 指向提交的日期——两条合起来就是上面这张表的原始数据。

这张表支持不了的四件事
  • 版本号印不出来。全站卫生检查拒绝 HTML 里出现字面版本号 （scripts/check-site.py 的 versions 断言）， 理由不是洁癖：写死的版本号一定会过期。于是这一页用日期 + 功能 定位每一次发布，当前版本走 data-site-version 占位符。 完整的逐版清单（每个 tag、两个日期、CHANGELOG 的一句话）在 site/data/timeline.json 里，由 git tag 与 CHANGELOG 生成，页面不手抄。
  • 6 条 CHANGELOG 条目没有 tag。最早的两个 LSP 版本、括号 hover 那一版、 「当前光标处」goal 组那一版、希腊字母显示那一版，加上多文件 import 那一版。其中只有 import 那一版是用户可见的大版本——它有功能、有日期， 没有 tag，这一页就不声称它有 tag。
  • 「装了什么」是折叠文本，不是全文。数据里每条只收 CHANGELOG 首条 bullet，超过 240 字标 truncated: true；上表的中文摘要又是对这些 bullet 的转述。要看完整条目，读 editor/vscode/CHANGELOG.md（1336 行）。
  • 同一天内的先后顺序看不出来。聚合按天，一天 24 个 tag 时谁先谁后 要回 git 看；这一页只保证「这一天装了什么」不错。

§4 一次发布留下 26 个资产

推一个 tag，release.yml 跑一遍，GitHub Release 上就有 26 个文件。 这个数字是当场量的：gh release view <tag> --json assets -q '.assets | length' → 26（docs/RELEASE.md 里还写着 25，那是旧的）。 构成是 8 个 CLI tarball + 8 个 LSP tarball + 9 个 VSIX + 一份校验和清单。

8 个平台三元组怎么构建，外加一个不含二进制的回退包。除 universal 包外，每个平台同时产出 CLI 与 LSP 两个 tarball，以及一个内嵌这两个二进制的平台 VSIX。
平台（VSIX target） Rust target triple 怎么构建
darwin-arm64 aarch64-apple-darwin macos-latest 原生 cargo build
darwin-x64 x86_64-apple-darwin 同上
win32-x64 x86_64-pc-windows-msvc windows-latest 原生构建
win32-arm64 aarch64-pc-windows-msvc 同上
linux-x64 x86_64-unknown-linux-gnu cargo-zigbuild + 显式 glibc 2.28 地板，构建后 readelf 断言最高符号版本不超过它
linux-arm64 aarch64-unknown-linux-gnu 同上
alpine-x64 x86_64-unknown-linux-musl Zig 静态链接，构建后 ldd 必须是 not a dynamic executable
alpine-arm64 aarch64-unknown-linux-musl 同上
（universal） 无（回退包） 不内嵌二进制；装到没被上面覆盖的平台（如 linux-armhf）时，按版本锁定下载兜底

glibc 地板与静态 musl 都不是洁癖：ubuntu-latest 原生构建会带上 2.39 的符号， 老发行版装不上；而 Alpine 根本没有 glibc。两条都有构建后的断言守着，不是写在文档里的承诺。

资产名 个数 是什么
sokonanoda-cli-<rust-target>.tar.gz 8 sokonanoda 裸二进制，agent 与 headless 直接执行，不需要 cargo
sokonanoda-lsp-<rust-target>.tar.gz 8 语言服务器裸二进制，也是 universal 包回退下载的目标

§4.1 下载之后自己验一遍

两条独立的路：校验和证明文件没被改动（完全离线，一个哈希工具就够）， 构建来源证明证明它确实由本仓库该 tag 的 workflow 产出 （用 gh 核对，需要 gh ≥ 2.49，首次还要能取到 Sigstore 的信任根）。 

$ V=$(grep -m1 '^version' Cargo.toml | cut -d'"' -f2)
$ gh release download "v$V" -R ColorlessBoy/sokonanoda-lang \
    -p 'sokonanoda-cli-aarch64-apple-darwin.tar.gz' -p SHA256SUMS
$ grep 'sokonanoda-cli-aarch64-apple-darwin' SHA256SUMS | shasum -a 256 -c -
$ gh attestation verify ./sokonanoda-cli-aarch64-apple-darwin.tar.gz \
    -R ColorlessBoy/sokonanoda-lang

$ 是提示符，不用输入。第一条从仓库里取当前版本， 第二条按那个 tag 只下载你点名的那两个文件。校验和：macOS 用 shasum -a 256， Linux 与 CI 用 sha256sum -c -，Windows 用 Get-FileHash 对照清单。

清单里只有一行是你下载的那个文件，所以用 grep 过滤后再 -c—— 直接对整份清单跑 -c 会因为另外 25 个文件不在本地而报一堆「找不到」。

§4.2 为什么钉版本，为什么禁用 latest

这条发布链有一个不变量：tag == Cargo.toml == package.json == VSIX 里内嵌的 LSP 二进制版本。打包前 release.yml 的 version gate 会断言 tag 与两处版本一致；仓库里另有一条契约测试 cargo_and_extension_versions_match 守着那两处不漂。

所以扩展的下载路径写死成 releases/download/v${extensionVersion}/…， 永不取 latest——这句话直接写在 editor/vscode/server.js 的注释里。跟着 latest 走意味着扩展与服务器 可能不同版本，而这个项目对不上就拒绝运行：启动器的缓存标记与版本钉不一致时 exit 3 并给人话， 绝不猜一个版本。钉版本是策略，不是遗漏。

  • tag = Cargo.toml = package.json = 内嵌 LSP

§5 一次发布怎么发生

人只做前三步，其余全自动。这条链从 2026-09-13 起就没有手工发布步骤了。

  1. 改两处版本：Cargo.toml 的 [workspace.package].version 与 editor/vscode/package.json 的 version，两处必须一致。
  2. 补一条 editor/vscode/CHANGELOG.md 条目——§3 那一列「装了什么」就是它。
  3. push 到 main。
  4. ci.yml 的 lint 与 test 全绿后，auto-tag job 发现 Cargo.toml 的版本还没有对应 tag，就打上 v<版本> 并 dispatch release.yml。这一步必须显式 dispatch：用 GITHUB_TOKEN 推的 tag 不会触发 workflow，而 workflow_dispatch 是那条规则的例外。
  5. release.yml 四个 job，但**不是一条直线**：build（8 个平台）→ package-vsix（version gate + 9 个 VSIX + 冒烟）；此后 github-release（26 个资产 + SHA256SUMS + 来源证明）与 marketplace-publish（先 universal、后平台包，逐包重试 4 次）**并行**—— 前者的 needs 是 [build, package-vsix]，后者只 needs [package-vsix]。

手动推 tag 只作应急（跨版本热修）。另有 workflow_dispatch 的 dry-run： build 与 package-vsix 照跑，9 个 VSIX 作为 workflow artifact 下载， 但不建 Release、不上架——想验证打包本身而不发版时用它。

出处：.github/workflows/ci.yml、.github/workflows/release.yml、 docs/RELEASE.md。上架那条腿的已知风险是外部服务抖动： Marketplace 的 Azure gallery 端点间歇超时，所以每个包独立重试 4 次 ×30 秒。
